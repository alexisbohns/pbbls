## Verdict

Against that, the strongest structural asset is agentic-development readiness: the product map is CI-gated (AGT-02 at level 4) and cross-user reads are enumerated jsonb allowlists proven by runnable field-set harnesses (PRV-07 at level 4), so the two verified level-4 criteria are both real. Between those poles sit the surface's recurring themes: no CI gate runs web lint or tests at all, security headers are entirely absent, collection writes are stitched client-side against the repo's own RPC-first rule, and a failed store load renders the first-run empty state so a user with years of entries is shown a "record your first pebble" screen. The surface scores 48 (grade D), dragged down by Safety (32, E), Performance (37, E), and Platform (35, E). Eleven open High findings sit across SEC, GDP, SAF, TST, A11Y, and REL; each would cap its domain at B, but every one of those domains already scores at or below D so no cap actually binds. #### 🟠 F-2026-08-SEC-web-01 Stored XSS: user-controlled glyph stroke `d` is interpolated raw into server-composed render_svg and injected via dangerouslySetInnerHTML on anonymous and cross-user surfaces

- **Criterion:** SEC-05 (Injection-safe input handling at trust boundaries)
- **Priority:** P1 · **Cost:** M · **Impact x Likelihood:** 5 x 3 = 15
- **Where:** `packages/supabase/supabase/functions/_shared/engine/glyph.ts:255`; `packages/supabase/supabase/functions/_shared/compose-and-write.ts:122-128`; `apps/web/components/connections/ConnectionPebbleTile.tsx:41`; `apps/web/components/shared-pebble/SharedPebbleView.tsx:56`; `apps/web/components/pebble/PebbleVisual.tsx:84`; `apps/web/components/path/PathStone.tsx:132`; `packages/supabase/supabase/migrations/20260411000001_core_tables.sql:45,190` (glyphs_insert RLS)
- **Why it matters:** `glyphs.strokes` is jsonb with no CHECK and is user-writable under `glyphs_insert` RLS (`user_id = auth.uid()`), so an authenticated attacker can PATCH/POST arbitrary stroke objects. The compositor builds `render_svg` by string-interpolating each stroke `d` verbatim into an SVG `<path>`, so a `d` like `M0 0"/><foreignObject><img src=x onerror=...></foreignObject><path d="` breaks out of the attribute and injects active markup. That value is set via `dangerouslySetInnerHTML` with no sanitization on the anonymous share page and on a connection's pebble rendered inside the viewer's authenticated session, using the attacker's own glyph on their own pebble (no marketplace approval needed). Client-side glyph rendering is safe (React escapes JSX), which is exactly why this string-built sink stands out.
- **Fix:** Sanitize at composition (parse and re-emit each stroke `d` from a numeric path grammar, rejecting anything outside the SVG path token set) before interpolation; as defense in depth run `render_svg` through a server-side SVG sanitizer or `DOMPurify(svg,{USE_PROFILES:{svg:true}})` at every sink; add a hostile-input fixture asserting the stored `render_svg` is inert.
- > Verification (CONFIRMED): Independently reproduced the full stored-XSS chain end to end. SOURCE: glyphs.strokes is jsonb with no CHECK (core_tables.sql:45) and glyphs_insert/update RLS is bare user_id=auth.uid() (lines 190-193), so an authenticated attacker writes arbitrary stroke.d via PostgREST or via create_pebble's inline new_glyph path (visibility_grades.sql:167-175, which also sets attacker-controlled view_box to satisfy the "0 0 200 200" gate at compose-and-write.ts:76). No marketplace approval: can_use_glyph passes for an authored glyph. SINK: glyph.ts:255 interpolates d="${stroke.d}" with no escaping; I hand-traced the payload M0 0"/><foreignObject><img src=x onerror=...></foreignObject><path d=" through all composePebble transforms (stripFills touches only fill=, monochromeStrokes only stroke=, namespaceIds only <path> id=, extractSvgInner preserves inner) and the injected foreignObject/img survives untouched, then is written to pebbles.render_svg (compose-and-write.ts:122-128). DELIVERY: all four client sinks set dangerouslySetInnerHTML with render_svg and no sanitizer (SharedPebbleView.tsx:56, ConnectionPebbleTile.tsx:41, PebbleVisual.tsx:84, PathStone.tsx:132); the three web "sanitiz" hits are draft-reference reconciliation, not HTML sanitization; no DOMPurify on this path. Aggravating factors beyond the finding: the app is a Serwist PWA storing the Supabase session JWT in localStorage on the pbbls.app origin, so XSS even on the anonymous share page reads the token of any logged-in user who opens the link (account takeover from one click, no connection precondition), and compose-pebble-update feeds the identical path.
