## Verdict

The worst finding on this surface is not a leak but a wellbeing failure: the record flow answers every emotional state identically, celebrating a first maximum-negative entry with a full-screen "Achievement unlocked, First [Sadness]" card and a "+N karma" flash, while the app ships zero crisis or helpline resources in any locale (SAF-android-01, verified, risk 16). Around it sit a cluster of store-and-regulatory gaps that all trace to the same root: signup collects no age gate and no Art. 9 explicit consent, Google OAuth accounts record no consent metadata at all, there is no in-product reporting mechanism where other users' content renders, and production failures reach no monitored destination. The best structural strength is genuinely strong: architecture (ARC 77, B) and agentic-development readiness (AGT 78, B) are the surface's anchors, with RPC-first atomic writes (REL-03, ARC-02), ktlint-enforced conventions (ARC-04, level 4), a CI-enforced localization parity test (A11Y-07), and injection-safe trust boundaries with hostile-case tests (SEC-05). Android faithfully mirrors iOS 1:1, which is both the discipline and the hazard here: the illegible dark-theme Google button and the passwordless-current password rotation are bugs ported verbatim to both store apps. The overall score of 50 (grade D) reflects a well-built client whose security, privacy, GDPR, safety, and store-compliance dimensions (the four the Pebbles profile weights hardest) are all held down by absent process and unshipped legal machinery rather than by bad code.

- **Fix:** Make preview block-aware in the blocked-viewer to blocker direction, returning the same unusable-token status shape as expiry (the blocker to blocked direction can stay live to avoid the reverse oracle); add both directions to a future block-matrix harness.

### 🟢 F-2026-08-REL-android-07 (REL-04) Snap upload retry is non-idempotent after a partial success: the surviving rendition blocks every retry

- **Criterion:** REL-04 Idempotence and double-submit protection
- **Priority:** P2 · **Cost:** S · **Impact x Likelihood:** 2 x 2 = 4
- **Where:** `apps/android/app/src/main/kotlin/app/pbbls/android/services/PebbleSnapRepository.kt:69-92 (parallel uploads, upload { contentType = ... } with no upsert), :46-48 (doc: 'The bucket has no UPDATE policy, replace is delete + re-upload'); features/pebblemedia/SnapUploadCoordinator.kt:153-177 (retry re-runs the same uploadProcessed to the same prefix), :97-102 (retryCurrent same id).`
- **Why it matters:** uploadProcessed uploads original.jpg and thumb.jpg in parallel and throws if either fails; on a flaky network one rendition can land while the other fails, then the auto-retry (and the user's manual retry) re-uploads both to the same paths without upsert, and the pebbles-media bucket deliberately has no UPDATE policy, so the already-stored object makes the retry fail permanently. The chip sits in FAILED forever under retry taps; the only recovery is removing the photo and re-picking it, which nothing tells the user to do. The retry path exists precisely for flaky networks, the one condition under which it cannot converge.
- **Fix:** Make the retry idempotent (best-effort delete both objects before re-uploading, using the existing deleteFiles, or treat an already-exists response on a rendition as success for that half); mirror on iOS since the coordinator is ported verbatim.
