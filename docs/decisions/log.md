# Decision log

Append-only ledger of **significant** product/engineering decisions. One terse entry per decision.

**Significance bar:** would a future agent or human waste real time rediscovering or wrongly reversing this?

**Rules:**
- Append-only. Newest entries at the bottom.
- **Supersede, don't edit.** Status changes are new appended entries that reference the prior one — never edits to past entries.
- Keep entries terse. If a decision needs prose, link to the PR/issue under **Refs**.
- Skip routine choices, style nits, and anything obvious from the code.

## Entry template

```markdown
## YYYY-MM-DD — <decision title>

- **Status:** taken | rejected | deprecated | superseded-by(YYYY-MM-DD title)
- **Scope:** ios | webapp | db | infra | docs (one or more, comma-separated)
- **Context:** the scope, issue, or challenge — a contextual *why now*.
- **Decision:** the "we will …" formula. What we decided, stated as an action.
- **Why:** why this option and not the alternatives.
- **Consequences:** the "how" — what follows from this decision (constraints, follow-ups, things to watch).
- **Supersedes / Superseded-by:** link to the entry this replaces, or `—`.
- **Refs:** #PR, #issue, file paths.
```

## 2026-05-26 — Ban `+` in email addresses across auth surfaces

- **Status:** taken
- **Scope:** ios, webapp
- **Context:** Gmail-alias sub-addressing (`user+anything@gmail.com`) lets one inbox spawn unlimited Pebbles accounts. RFC 5322 and Supabase both accept `+`, so the server is not the authority on this rule.
- **Decision:** We will strip `+` from email input on every keystroke/paste, reject any submitted address containing `+` with a `canSubmit`-style guard, and show a localized inline error explaining the restriction.
- **Why:** Prevents multi-account abuse via alias sub-addressing. Silent stripping alone would confuse users whose typed character disappears, so the inline error is mandatory. Lowercasing and whitespace trimming stay silent on purpose — only `+` warrants explanation.
- **Consequences:** Every new email input surface needs both real-time stripping AND a submit-time guard (autofill paths can bypass the binding's normalization). Relaxing the rule (e.g. allowing `+` for non-Gmail domains) is a product decision — ask before changing.
- **Supersedes / Superseded-by:** —
- **Refs:** `apps/ios/Pebbles/Features/Auth/AuthView.swift` (`normalizeEmailInput`).

## 2026-05-26 — Deploy to remote Supabase instead of local Docker

- **Status:** taken
- **Scope:** db, infra
- **Context:** The standard Supabase local dev workflow (`supabase start`, `supabase functions serve`, `db:reset`) depends on Docker, which is a constant source of friction on the maintainer's machine.
- **Decision:** We will test edge functions, migrations, and DB changes against the remote Supabase project rather than local containers. Use `supabase db push` for migrations and `supabase functions deploy` for edge functions.
- **Why:** Docker workflows fail often enough that they block work; the remote project is reliable and cheap to iterate against for this team size.
- **Consequences:** Plans, verification steps, and onboarding instructions are written for remote-first workflows. Anyone proposing a local-Docker step should first confirm it works end-to-end on the maintainer's setup.

- **Refs:** —

## 2026-05-26 — Prefer RPCs for multi-table or multi-statement Supabase writes

- **Status:** taken
- **Scope:** db, webapp, ios
- **Context:** Client-stitched multi-table writes are not atomic — PostgREST has no client-side transactions, so a partial failure leaves the database inconsistent. RLS-only ownership checks are also harder to keep symmetric across surfaces.
- **Decision:** We will check `packages/supabase/supabase/migrations/` for an existing RPC before writing any Supabase query that touches more than one table or does more than a single-row `select`/`insert`/`update`/`delete`. If none exists, create one rather than chaining client calls. Keep sibling RPCs symmetric (e.g. payload keys added to `update_pebble` should also land in `create_pebble`).
- **Why:** RPCs run in a single Postgres transaction and can enforce ownership checks via `security definer`. They give us atomicity, a single source of truth for business rules, and surface parity between web and iOS.
- **Consequences:** Single-table, single-statement reads/writes stay as direct client calls — no RPC needed. Extending an existing RPC is preferred over re-implementing logic client-side, even when the RPC is missing a small piece of what you need.
- **Supersedes / Superseded-by:** —
- **Refs:** `AGENTS.md` ("Supabase — prefer RPCs for multi-table writes"), `packages/supabase/supabase/migrations/`.

## 2026-06-29 — Karma wallet: one ledger, debt allowed, refunds server-only

- **Status:** taken
- **Scope:** db, webapp
- **Context:** Making karma spendable (M36 Pebblestore, #494) required turning the earn-only `karma_events` ledger into a currency with a balance that can go down — without breaking existing flows (notably pebble deletion, which claws back the karma a pebble earned).
- **Decision:** We will keep **one ledger** (`karma_events` gains a `type` credit/withdraw axis keyed off movement *category*, not sign) with a single balance = Σ delta, snapshotted in `wallet_balances`. The non-negative rule lives **only in the `spend_karma` RPC** (row-locked `balance ≥ amount` check); there is deliberately **no `CHECK(balance >= 0)`** on the snapshot, so earn-side clawbacks may drive the balance **negative (a debt)** the user clears by re-earning. `refund_karma` is **`service_role`-only**, never callable by `authenticated`.
- **Why:** Coupling pebble deletion to wallet state would be wrong UX, so clawbacks must always apply even into the negative — a column `CHECK` would roll back a legitimate delete. The purchase guard alone keeps the store safe (a negative balance can't buy anything). An unguarded `refund_karma` granted to `authenticated` is a karma-minting hole (`refund_karma(1_000_000, …)`); refunds are admin/server actions, and the buy flow needs no client refund because a failed grant rolls back the spend in the same transaction.
- **Consequences:** **Do not add `CHECK(balance >= 0)` to `wallet_balances`** — it would break pebble deletion. New spend-side reasons go through `spend_karma`; new earn-side reasons just insert credit events. The `bounces` admin snapshot trigger now folds **credits only** so "bounce karma distribution" keeps meaning *earned*. `delta` stays `smallint` (widening would force dropping/recreating dependent views on the live DB). Idempotency of a *purchase* is the caller's (sub-project C's) responsibility, enabled by `spend_karma` being callable inside the caller's transaction.
- **Supersedes / Superseded-by:** —
- **Refs:** #494, `docs/superpowers/specs/2026-06-29-issue-494-karma-wallet-design.md`, `packages/supabase/supabase/migrations/20260629192621_karma_events_type_axis.sql` … `20260629194621_wallet_summary_and_bounce_credit_only.sql`.

## 2026-06-29 — Web in-app notifications: Sonner + explicit-fire, no realtime

- **Status:** taken
- **Scope:** webapp
- **Context:** M36 sub-project B (#495) needed a non-invasive in-app activity primitive, first used for a "+N karma" pill on wallet credit. A web PWA cannot render into the iOS Dynamic Island, so the admired Opal effect had to be approximated within web limits, and we needed a way to know when a credit happened.
- **Decision:** We will build in-app activity on **Sonner** (ported from `apps/admin`), rendering a compact custom pill via `toast.custom()` bottom-center. The trigger is **explicit fire at the action site** via store-diff: the pebble mutation hooks read karma from provider truth before/after the action and call `notifyKarma(delta, reason)` on a positive delta. No Supabase realtime, no central balance-watcher.
- **Why:** Sonner gives queueing, timeout, swipe-dismiss, `aria-live`, and reduced-motion handling for free. Explicit fire is the cleanest feature-agnostic primitive (carries a reason label, no false-fire surface), needs no backend change, and suits a personal PWA where credits come from the user's own on-device actions. Realtime would be heavier and double-fire against the optimistic store reload.
- **Consequences:** New credit sources surface a pill by adding one `notifyKarma(...)` call at their action site — and must wire it on the hook the live surface actually uses (enrichment goes through the singular `usePebble(id)`, not `usePebbles()`). Credit-only by design: clawbacks (delta ≤ 0) stay silent. The pill uses a stable toast id so a new credit replaces the prior one. Reused by C (e.g. "glyph purchased") via the same primitive.
- **Supersedes / Superseded-by:** —
- **Refs:** #495, `docs/superpowers/specs/2026-06-29-issue-495-in-app-activity-design.md`, `apps/web/lib/activity/karma-activity.tsx`, `apps/web/components/activity/KarmaActivityPill.tsx`.

## 2026-06-30 — Glyph marketplace: use-rights entitlements, per-listing price, atomic buy

- **Status:** taken
- **Scope:** db, webapp
- **Context:** M36 sub-project C (#496) makes community glyphs the first thing the Pebblestore sells — buyable with karma over A's spend rails. We had to decide what a purchase grants, where price lives, and how to keep the spend+grant consistent.
- **Decision:** Buying grants a **use-rights entitlement** (`glyph_entitlements` row), **not a copy** — the original glyph stays single-source and the creator keeps authorship. **Price lives on the listing row** (`glyph_submissions.price`, flat-defaulted to 25 via a constant mirrored in `apps/web/lib/config/glyphs.ts`), read server-side by `buy_glyph` so the client can't set it. Each purchase snapshots **`price_paid`** on the entitlement. The **`buy_glyph` RPC** does spend (`spend_karma`) + entitlement insert in **one transaction**, idempotent via `unique(user_id, glyph_id)`.
- **Why:** Entitlements avoid stroke duplication and keep authorship/attribution clean, and make a glyph usable everywhere own glyphs are (picker + lookup map). Per-listing price (vs a single global constant) lets D re-price one glyph later with no schema change while staying flat now. `price_paid` preserves a per-glyph purchase ledger (buyers-per-month, revenue) that survives future price changes — so "glyph value" can be a derived aggregate, never a stored column (YAGNI: capture data, defer analytics). Single-transaction buy + the unique constraint make a concurrent double-buy roll back the loser's spend too, so a buyer is charged at most once.
- **Consequences:** New store goods (themes, pebbleskins) reuse the `buy_glyph` shape: validate listing → `spend_karma(price,'purchase',ref)` → grant, in one txn. Entitlement rows are insertable **only** via the `security definer` RPC (no INSERT policy). The purchase fires a dedicated **spend** pill (`notifyGlyphPurchased`), not credit-only `notifyKarma`. Market stays empty until a submission is `approved` (no moderation UI in C — that's D).
- **Supersedes / Superseded-by:** —
- **Refs:** #496, `docs/superpowers/specs/2026-06-30-issue-496-glyph-marketplace-design.md`, `packages/supabase/supabase/migrations/20260630003348_glyph_marketplace.sql`.

## 2026-06-30 — Glyphs become readable when listed/entitled; listed glyphs are creator-immutable (D8)

- **Status:** taken
- **Scope:** db
- **Context:** A community market means other users must read a creator's glyph rows (strokes/viewBox) to render and buy them — but glyphs were own-only readable. And once a glyph is listed/bought, letting the creator edit its strokes would be bait-and-switch on what buyers paid for.
- **Decision:** The `glyphs` SELECT policy widens to **own ∪ system-seeds (`user_id is null`) ∪ approved-listed ∪ own-entitled** — the single place community glyph rows become readable. The `glyphs` UPDATE/DELETE policies are rewritten to **lock** a glyph once it has an active submission (`pending`|`approved`) **or** any entitlement: only `is_admin(auth.uid())` may then modify it; the creator cannot. The market view `v_glyph_market` is `security_invoker` so the caller's RLS applies.
- **Why:** The widened SELECT exposes *only* glyphs that are genuinely listed or that the caller already bought — no broad leak. The lock is backend-enforced (RLS), not UI-only, because a frontend-only guard is bypassable via the raw update path; `on delete cascade` would otherwise let a creator wipe buyers' entitlements. Admins are exempt because curating/adjusting listed glyphs is D's domain.
- **Consequences:** **Do not narrow `glyphs_select` back to own-only** — the market and picker depend on the widened policy. Future market goods must keep their listed rows readable the same way. The web UI reflects the lock (`GlyphDetail` hides edit/delete, shows a "Listed — locked" badge) but RLS is the real enforcement. Admin moderation that re-prices or edits listed glyphs (D) relies on the `is_admin` exemption.
- **Supersedes / Superseded-by:** —
- **Refs:** #496, `packages/supabase/supabase/migrations/20260630003348_glyph_marketplace.sql` (glyphs policy rewrite, `v_glyph_market`).

## 2026-06-30 — Admin glyph moderation: is_admin RPCs, first-party admin-owned glyphs, stroke-only SVG import (#497)

- **Status:** taken
- **Scope:** db, admin, webapp
- **Context:** M36 sub-project D builds the back-office for the glyph market: moderating community submissions (approve/reject/re-price) and seeding the market with first-party glyphs uploaded from raw SVG. Two frictions had to be resolved: the widened `glyphs` SELECT policy (D8, #496) does **not** let an admin read a *pending* submission's strokes via RLS, and the glyph model is **stroke-only** (paths render as outlines recolored by emotion) while most real-world SVGs are fill-based.
- **Decision:** All admin mutations go through **`is_admin`-gated `SECURITY DEFINER` RPCs** (`approve_glyph`/`reject_glyph`/`set_glyph_price`/`publish_admin_glyph`), plus a read RPC **`admin_list_glyph_submissions`** that joins glyph geometry server-side to bypass the pending-read RLS gap. Reject requires a reason stored in a new `glyph_submissions.review_note` column, surfaced to the submitter on the web "Mine" tab. First-party uploads are **owned by the admin user** (a normal auto-approved listing), **not** `user_id IS NULL` system seeds — so they reuse all market plumbing, `cannot_buy_own` protects the admin, and the D8 admin-exemption lets them be re-edited/re-priced. SVG import is **stroke-only**: a documented subset (`<path>/<line>/<polyline>/<polygon>`, path commands `M L H V Q C Z`) is converted; fills and other elements are skipped-and-reported; filled icons import as outlines. Adjust transforms (scale/recenter/flip) are baked into path coordinates at publish.
- **Why:** A `SECURITY DEFINER` read RPC is the only way to give admins pending-submission previews without weakening the marketplace SELECT policy. Admin-owned (vs system-seed) first-party glyphs avoid special-casing the buy/lock paths. Stroke-only import keeps the engine unchanged (a filled-glyph render mode would ripple across web + iOS — deferred); making the limit visible in the live preview is honest UX. Baking transforms into geometry means downstream renderers need no awareness of the adjust step.
- **Consequences:** New admin-curated store goods reuse this RPC shape (gated read + gated mutations). `review_note` is now part of the submission contract (web reads it via the existing submitter RLS). A filled-glyph render mode remains a future, separate decision. The admin SVG path parser supports only the documented command subset; arcs/smooth curves are skipped, not approximated.
- **Supersedes / Superseded-by:** —
- **Refs:** #497, `docs/superpowers/specs/2026-06-30-issue-497-admin-glyph-moderation-design.md`, `docs/superpowers/plans/2026-06-30-admin-glyph-moderation.md`, `packages/supabase/supabase/migrations/20260630084718_admin_glyph_moderation.sql`.

## 2026-07-01 — Glyph sales pay the creator via a net-zero karma transfer; attribution transfers ownership (#497)

- **Status:** taken
- **Scope:** db, admin, webapp
- **Context:** M36 sub-project D gained curation needs: creators should earn from glyph sales, admins should be able to attribute a first-party (admin-uploaded) glyph to the real creator, delist a glyph without deleting it, and hard-delete glyphs.
- **Decision:** A glyph sale **credits the glyph owner (`glyphs.user_id`) the full price** as a `glyph_sale` karma credit inside `buy_glyph`, in the same transaction as the buyer's `spend_karma` withdraw — a **net-zero transfer** (no minting), consistent with the wallet rules (#494). **Attribution transfers ownership**: `admin_attribute_glyph` sets `glyphs.user_id` to a looked-up user, so they become the creator (glyph appears in their gallery, `cannot_buy_own` protects them, payouts route to them); admin-owned (unattributed) glyphs pay the admin account. **Delisting** is a new `glyph_submissions.listed` flag: `v_glyph_market` + `buy_glyph` require `approved AND listed`, so a delisted glyph leaves the market but existing owners keep it. **Delete** is a `security definer` admin RPC that cascades to the submission + entitlements.
- **Why:** Reusing `glyphs.user_id` as the payout target (rather than a separate `credited_to`) keeps ownership, gallery visibility, `cannot_buy_own`, and payouts consistent from one column. Crediting inside `buy_glyph` (vs a separate call) makes the transfer atomic with the spend. Net-zero keeps the economy closed. A `listed` flag (vs flipping `status`) preserves the `approved` audit + entitlements while removing buyability.
- **Consequences:** New `glyph_sale` reason on the `karma_events` CHECK. Payout amount is bounded by `delta`'s `smallint` (same as the existing spend path). Delisting is reversible; deletion is not (buyers lose access — the admin UI warns). Future royalty/revenue-share models would build on `glyphs.user_id` as the creator.
- **Supersedes / Superseded-by:** —
- **Refs:** #497, `packages/supabase/supabase/migrations/20260701102810_glyph_marketplace_curation.sql`.

## 2026-07-01 — Deprecated the glyph shape: dropped glyphs.shape_id and the pebble_shapes table (#503)

- **Status:** taken
- **Scope:** db, ui, ios
- **Context:** A glyph is strokes in a square viewBox scaled into the pebble slot at render time (issue #278). The `glyphs.shape_id` FK to `pebble_shapes` was long deprecated — every surface (web /carve, admin upload, iOS carve, the system seeds) already wrote `shape_id = null`, and pebble *outlines* are rendered from baked-in engine templates (`apps/web/lib/engine/templates.ts`), not from `pebble_shapes`.
- **Decision:** Dropped `glyphs.shape_id` and the now-orphaned `pebble_shapes` table system-wide. Updated the dependent RPCs/views to stop referencing the column: `create_pebble` no longer reads `new_glyph.shape_id`; `publish_admin_glyph` lost its `p_shape_id` parameter; `admin_list_glyph_submissions`, `v_pebbles_full`, and `v_glyph_market` no longer project `shape_id`. Removed all web/admin readers (`Mark.shape_id`, provider mappings, `PEBBLE_SHAPES` config, `useShapeName`, the dead `carve/PebbleOutline.tsx`, shape i18n strings) and tidied iOS comments/tests.
- **Why:** No live data flowed through `shape_id` — it was pure backward-compat cruft, and `pebble_shapes` had no reader after the FK went away. Removing both eliminates a misleading data model (glyphs are shape-agnostic).
- **Consequences:** Legacy glyph rows keep their original (sometimes non-square) `view_box`; they render fine because the engine fits by viewBox. Geometry was intentionally NOT normalized. Reintroducing a glyph→shape association is out of the question — glyphs are squares.
- **Supersedes / Superseded-by:** —
- **Refs:** #503, `docs/superpowers/specs/2026-07-01-remove-glyph-shape-design.md`, `docs/superpowers/plans/2026-07-01-remove-glyph-shape.md`, `packages/supabase/supabase/migrations/20260701114205_drop_glyph_shape.sql`.

## 2026-07-01 — iOS karma-earned flash is an in-app pastille, not a Dynamic Island Live Activity (#505)

- **Status:** taken
- **Scope:** ios
- **Context:** #505 set out to surface the "+N karma" earn (creating/enriching a pebble) as an ActivityKit **Live Activity in the Dynamic Island**, mirroring Opal. The spec (D3) treated the Live Activity as the primary presentation with an in-app capsule only as a non-Dynamic-Island fallback. On-device testing (iPhone 15, iOS 26) showed `Activity.request` succeeding (`state=active`) but **nothing rendering** in the notch, on the Lock Screen, or when backgrounded within the window.
- **Decision:** Abandon the Live Activity for the karma flash. The flash is now **always an in-app "liquid glass" pastille** popping bottom-center, hosted in a **pass-through `UIWindow`** (level `.alert + 1`) so it floats above the create/edit/detail sheets that are up at earn time. Presentation uses real `.glassEffect` on iOS 26 behind a localized `if #available` guard (an approved, documented exception to the workspace "iOS 17 APIs only / no `if #available`" rule), with a translucent-material capsule fallback below 26. A Core-Haptics vibration is derived from the ceramic sound's amplitude envelope and fired in lockstep with it; an accent-color countdown ring drains over the pastille's ~2.5s lifetime. The DI-detection + LA-vs-capsule routing (`DeviceCapabilities`, `karmaPresentationDecision`) was deleted. The `PebblesWidget` app-extension target + `KarmaLiveActivityController` + `KarmaActivityAttributes` are **retained, unused**, as the reference for a future Glyph-purchase Live Activity.
- **Why:** iOS does not render a foreground app's own Live Activity in the Dynamic Island, and karma is **only ever earned by a foreground in-app action** — so the real DI can never show this flash. The concern was raised during brainstorming (Challenge 2), wrongly walked back, and confirmed by device evidence. An in-app pastille is the honest, cross-version (iOS 17+), every-device way to reproduce the Opal-style moment; a pass-through overlay window is required because the earn happens inside a sheet that a normal RootView overlay sits behind.
- **Consequences:** No App Group / push / provisioning burden for the karma flash. The retained Live Activity stack is dead code until the Glyph feature adopts it (a future notification that *can* surface while the app is backgrounded, where the DI works). The `if #available(iOS 26, *)` exception is scoped to one view modifier; adopting Liquid Glass more broadly, or raising the iOS floor to 26, remains a separate decision. The pastille amount still comes from the server `karma_delta` (unchanged).
- **Supersedes / Superseded-by:** Revises presentation decision **D3** of the #505 spec (Live Activity → in-app pastille); the server-delta (D1) and fallback-fork (D2) decisions stand.
- **Refs:** #505, `docs/superpowers/specs/2026-07-01-issue-505-ios-karma-earned-flash-design.md`, `docs/superpowers/plans/2026-07-01-ios-karma-earned-flash.md`.

## 2026-07-10 — Android app: native Kotlin + Jetpack Compose, mirroring the iOS architecture

- **Status:** taken
- **Scope:** android, docs
- **Context:** Pebbles wants an Android app matching the quality bar set by iOS. Candidates: React Native (the webapp is React), Flutter, or native Kotlin. The app will be built mostly by AI agents with human review, and the long-term vision is two platform-perfect native apps — no convergence of iOS+Android into one codebase.
- **Decision:** We will build the Android app in **native Kotlin + Jetpack Compose**, in `apps/android`, structured as a mirror of `apps/ios`: feature folders, injected service objects, hand-written `@Serializable` models mirroring the Postgres schema, **supabase-kt** for Auth/PostgREST/RPC/Storage, **rive-android** for the shared `packages/rive` assets, Gradle as the project source of truth, wrapped in npm so it participates in the Turbo monorepo like `@pbbls/ios`.
- **Why:** The real cross-surface contract is the database — business logic lives in Postgres RPCs (see 2026-05-26 "Prefer RPCs"), on which all stacks sit equally. React Native's reuse advantage is modest (a thin React-free data layer; the expensive work — custom SVG rendering, glyph canvas, animation/haptic feel — is per-platform in every option), Flutter adds a third language with zero reuse from any surface, and Kotlin Multiplatform only pays if the healthy 16k-LOC Swift app were refactored to consume shared Kotlin. Compose is the only Android option with zero abstraction tax on the deep-native work that defines the iOS quality bar (#505 pastille), and SwiftUI ↔ Compose are near-isomorphic, making the finished iOS app a directly portable reference implementation for agents.
- **Consequences:** Android joins the web+iOS lockstep cadence on schema/RPC changes ("keep sibling RPCs symmetric" now spans three surfaces). Models and query strings are hand-written per surface by design — do not build a codegen/shared-types bridge without a new decision. RN/Flutter proposals for Android are settled-rejected. Scaffolding `apps/android` (Gradle project, CI, auth + Path skeleton, `apps/android/CLAUDE.md` conventions) is a separate future milestone with its own issue and plan.
- **Supersedes / Superseded-by:** —
- **Refs:** `apps/ios/CLAUDE.md`, 2026-05-26 "Prefer RPCs for multi-table or multi-statement Supabase writes".

## 2026-07-11 — Android Nunito: one variable-font file, not four static weights

- **Status:** taken

## 2026-07-13 — Petroglyph wobble is generated at runtime on-device (iOS-first), as leaky filled outlines (#555)

- **Status:** taken
- **Scope:** ios, ui
- **Context:** #555 specs the handcrafted stroke (wobble + boil) and its §0 recommends **baking wobble at build time** so every platform ships identical static paths. But pbbls glyphs are user-carved and marketplace-traded (fully dynamic — build-time baking is impossible), pebbles are already server-composed into `render_svg` at write time, and a server-side (write-time) bake would iterate slowly (redeploy + backfill per look tweak), persist a wrong look across every platform at once, grow `render_svg` ~5–15×, and still miss the glyph-only surfaces (souls grids, glyph picker/market, carve preview) that bypass `render_svg`. Separately, the approved playground look bakes strokes into **filled outlines whose width breathes ("leaky")** — a stroked wobbled centerline (issue §2.3/§4's default contract) cannot reproduce that, and `trim()`-based draw-on cannot animate a fill.
- **Decision:** Wobble is computed **at runtime on-device**, starting as an isolated, Debug-only iOS module (`apps/ios/Pebbles/Features/Path/Render/Wobble/`, PR #556): SVG 1.1 §15.19 fractalNoise port → flatten (~2-unit chords) → dual-edge outline (caps/rings) → displace every contour point → fill. The displacement sign is **minus** (matching the playground bake / feDisplacementMap inverse sampling); issue §2.3's "+" is superseded. The appear animation is preserved as a fat trimmed **mask** stroking along the wobbled centerline, reusing `PebbleAnimationTimings` unchanged. Cross-platform parity is anchored by golden fixtures (`apps/ios/PebblesTests/Wobble/WobbleGolden.json`, regenerable only via `apps/ios/Scripts/generate-wobble-golden.mjs`) that the future Kotlin/TS ports must reproduce (LCG exact; turbulence/displacement ≤ 1e-9).
- **Why:** On-device generation keeps stored data pristine and the whole experiment disposable (delete the Wobble folders + six flag-gated call sites), covers all surfaces including client-side previews, adds zero payload, and makes boil trivial later (3 cached local variants, no data). The bake's parity guarantee is retained through the shared golden fixtures instead of a single implementation.
- **Consequences:** `render_svg` / `render_version` are untouched — do not bump the engine or backfill for wobble. Android/web ports must pass the golden fixtures before shipping (implementation drift is the accepted trade). Consolidating the same algorithm into the server engine later remains possible once the look freezes, but is a new decision (payload trade-off re-opens). Do not "correct" the displacement sign to match issue §2.3, and do not substitute another noise (simplex, GameplayKit, hash) — both change the approved look.
- **Supersedes / Superseded-by:** Supersedes the "bake at build time" recommendation of #555 §0 for this codebase, and the centerline-stroke render mode of its §4 contract (leaky filled outlines chosen instead).
- **Refs:** #555 (analysis comment of 2026-07-13), PR #556, `apps/ios/Pebbles/Features/Path/Render/Wobble/`, `apps/ios/Scripts/generate-wobble-golden.mjs`.

- **Status:** taken
- **Scope:** ios, ui, core
- **Context:** The app opened on a *fake* loader — a Rive logo (`pbbls-logo-appear_idle.riv`) held by a hardcoded ~2.5s timer, after which a separate real loader could still appear. #555 gave us the wobble/boil vocabulary; #598 decided the app should open with an actual handcrafted animation that loads. No spinner anywhere: the authed home feed renders the app background on first load while a `startSettled` cover holds over it until `onFirstLoad`, then crossfades out.
- **Why:** The loader now reflects real readiness instead of a guessed duration, brands the launch, and never shows a spinner. The event-based (count + readiness) transition is agnostic and scalable ("boil N times then settle") and avoids the brutal time-based cuts that duration math produced. Logo-specific gentle wobble params (amplitude 9 vs canonical 18) keep fine features clean without touching the shared glyph/pebble wobble.

## 2026-07-29 — Postgres views are `security_invoker` by default; `auth.uid()` filters are not a substitute (#616)

- **Status:** taken
- **Scope:** db, core, auth
- **Context:** `v_pebbles_full` shipped without `security_invoker`, so it ran with definer rights and bypassed RLS on `pebbles` and every joined table. Because this project never grants table privileges explicitly and relies on Supabase's default privileges for the `public` schema, `anon` inherited SELECT on the view too — a live probe with only the publishable key and **no session** returned 182 pebbles across 20 distinct users (names, descriptions, intensities, cards, souls, domains, snap paths), while the `pebbles` table itself correctly returned `[]`. The only scoping was the client-side `.eq("user_id", …)` in the web provider. This is the *second* occurrence of the class: `v_ripple` was patched the same way in #442.
- **Decision:** Every new or recreated view in `public` is created `with (security_invoker = true)` and paired with an explicit `revoke all … from public, anon` + `grant select … to authenticated` when it exposes user data. The bolt-on `where u.id = auth.uid()` pattern used by `v_karma_summary`, `v_bounce` and `v_ripple` is retained where it already works but is **not** the pattern to copy for new views.
- **Why:** A trailing `auth.uid()` filter only protects views whose shape happens to be one-row-per-user; it cannot scope a view that fans out over per-row child data, and it silently does nothing if a later `create or replace` drops it. `security_invoker` delegates to the base tables' RLS, which is already the reviewed source of truth, so the view cannot drift away from the policy. Default privileges mean "no explicit grant" is not "no access" — it is access for `anon`.
- **Consequences:** Reads through `v_pebbles_full` now depend on base-table RLS. This is safe by construction: `emotions`/`domains` are `using (true)`, and `can_use_glyph` (20260712000000) gates pebble glyphs to own ∪ system ∪ entitled, a strict subset of what `glyphs_select` permits — so no glyph disappears. `service_role` still bypasses RLS, so admin and analytics reads are unaffected. Client-side `.eq("user_id", …)` filters become redundant but stay harmless. A view audit at the time of this entry found no other unprotected view; `v_emotions_with_palette` remains definer-rights but exposes only `using (true)` reference data.
- **Supersedes / Superseded-by:** Generalises the one-off `v_ripple` hotfix (#442) into a standing rule for all views.
- **Refs:** #616, #442, `packages/supabase/supabase/migrations/20260729000000_v_pebbles_full_security_invoker.sql`, `20260516000001_v_ripple_security_filter.sql`, `apps/web/lib/data/supabase-provider.ts`.

## 2026-07-29 — Account deletion: anonymize externally-referenced glyphs via the `user_id = null` system state; delete personal ledger rows (#631)

- **Status:** taken
- **Scope:** db, api, auth, legal
- **Context:** M46 ships the store-blocking account deletion (Play policy + Apple 5.1.1(v)). A naive delete-everything hits three traps: buyers hold `glyph_entitlements` on the seller's glyphs (cascade would revoke paid-for content), `souls.glyph_id` is `ON DELETE RESTRICT` (another user's soul can reference the deleting user's glyph after an `admin_attribute_glyph` reattribution, so the delete would hard-fail), and `glyph_submissions.submitter_id` was `NOT NULL` (keeping the approved audit trail would block `auth.admin.deleteUser`).
- **Decision:** `purge_account(p_user_id)` — a service-role-only `security definer` RPC — deletes every user-owned row in FK order (own `glyph_entitlements` before `karma_events`; `pebbles`/`souls` before `glyphs`) in one transaction, returning per-table counts. Glyphs that are **externally referenced** (foreign entitlements ∪ foreign souls/pebbles/profiles ∪ domain defaults) are **anonymized** to `user_id = null` — the pre-existing system-glyph state — and their submissions delisted (`listed = false`) with `submitter_id` detached; everything else is deleted. Personal ledger rows are deleted; net-zero transfers survive in counterparties' rows. The `delete-account` edge function orchestrates purge → storage prefix `pebbles-media/{user_id}/` → `auth.admin.deleteUser`, in that order, idempotent and resumable (the auth row goes last because it is the caller's retry credential).
- **Why:** `user_id = null` is already readable and usable by everyone (`glyphs_select`, `can_use_glyph`), so buyers keep rendering with zero schema surface added. The predicate is deliberately wider than the roadmap's "sold" so the purge converges under every FK the schema actually has, not just the marketplace one. Delisting in the same transaction prevents the anonymized glyph from selling for nothing (`buy_glyph` skips the payout when the owner is null).
- **Consequences:** Anonymized glyphs become de-facto commons (usable by all) — accepted. `glyph_submissions.submitter_id` is now nullable; the admin list left-joins the email and shows detached rows blank. **Standing rule (roadmap §M46): every later milestone appends its new user-owned tables to the numbered sections of `purge_account` (marker in section 4) AND to the seed + assertions of `scripts/verify-account-purge.ts`** — the script is the regression harness. Accepted race: a `buy_glyph` committing mid-purge can leave a `glyph_sale` event that blocks `deleteUser`; the re-run converges.
- **Supersedes / Superseded-by:** —
- **Refs:** #631, `docs/superpowers/specs/2026-07-29-account-deletion-design.md`, `packages/supabase/supabase/migrations/20260729201326_account_deletion_purge.sql`, `packages/supabase/supabase/functions/delete-account/index.ts`, `packages/supabase/scripts/verify-account-purge.ts`, roadmap §M46 + §5 item 9.

## 2026-07-29 — Drafts: a separate jsonb table, never a status column on `pebbles`; local autosave is insurance only (#639)

- **Status:** taken
- **Scope:** db, core, webapp, ios, android
- **Context:** M47 ships quick capture ("just a name" is enough) plus per-surface composer autosave. The obvious-looking design — a `status` column on `pebbles` — collapses on contact with the schema, and the two features are easy to conflate into an offline-sync story that #620 has already ruled out.
- **Decision:** Drafts live in their own table, `public.pebble_drafts` (`user_id`, `payload jsonb`, `created_at`, `updated_at`), owner-only via a single `for all` policy, written by direct single-table client calls with no RPC. `payload` is a **partial `compose-pebble` wire payload** with unset keys omitted — the same shape on all three surfaces, so publishing is a pass-through: `compose-pebble` once, then delete the row (keyed off the returned `pebble_id`, so a soft-success 5xx also clears the draft). Local autosave persists that same shape **minus `snaps`** to `localStorage` / a caches-dir JSON file / SharedPreferences. Drafts relax *saving* only; publishing keeps its `name` + `emotion_id` gate.
- **Why:** `pebbles` has five NOT NULL semantic columns a draft may all lack (`name`, `happened_at`, `intensity`, `positiveness`, `emotion_id`); a status column would relax them for every real pebble and oblige every present and future view/analytics migration to carry a `status <> 'draft'` filter that silently leaks drafts into ripple, bounce, week groups and the KPI views the day someone forgets it. `create_pebble` is the schema's only `pebble_created` emitter and always emits, so keeping drafts off that path makes zero karma structural rather than a special case. `update_pebble` is coalesce-based and cannot null a scalar, so editing a draft *down* to fewer fields is impossible there while a wholesale jsonb replace is trivial. Anchoring the payload on the wire shape rather than on each platform's composer struct is what keeps three hand-written clients in agreement — the in-memory structs are not symmetric (iOS `UUID`/`Date`/singular `domainId`, Android `String`/`OffsetDateTime`, web flat `useState`).
- **Consequences:** `payload` is deliberately unvalidated — `create_pebble` stays the single validation authority, at publish time. Nothing protects the ids inside the jsonb, so **hydration sanitizes stale ids** (a soul or glyph deleted behind a draft's back is dropped on resume) rather than letting publish fail on an FK or `can_use_glyph`. Server drafts carry `snaps` because the bytes are already durable in `pebbles-media` at pick time; the consequence is that **"save as draft" must skip the cancel-time `snaps.cancelAndCleanup`** on iOS and Android, which would otherwise delete the object the draft references. Local autosave omits media on purpose: an intentional save earns durable media, an accidental crash recovery does not. `happened_at` is stored and published verbatim — web's `isNow()` re-stamp is not applied to a resumed draft, so publishing hours later does not move the pebble to publish time. Drafts get their own list surface, never an inline timeline section, because the timeline's week grouping, ripple, bounce and stats all assume real pebbles. Per the M46 standing rule, `pebble_drafts` is appended to `purge_account` section (4) and to `verify-account-purge.ts`; `delete-account` needs no change (draft snaps already sit under the `pebbles-media/{user_id}/` prefix it sweeps).
- **Supersedes / Superseded-by:** Builds on 2026-07-29 "Offline is a non-goal on every surface" (#620) — this entry is what that one anticipated; it does not relax it.

## 2026-07-30 — Cross-surface data shapes are tested with foreign payloads, and timestamps are parsed tolerantly (#651)

- **Status:** taken
- **Scope:** ios, android, webapp, db, docs
- **Context:** `pebble_drafts.payload` (#639) is the first shape written *and read* by all three hand-written clients. They disagree on sub-second precision: web `new Date().toISOString()` emits milliseconds, Postgres `timestamptz` via PostgREST emits microseconds, iOS `ISO8601DateFormatter` with `.withInternetDateTime` emits whole seconds. A single formatter parses exactly one of those. M47 shipped iOS decoding with the non-fractional formatter, so **every web- and Postgres-written `happened_at` silently decoded to `nil`** and a resumed draft lost the timestamp it was captured at — breaking the same milestone's "publish verbatim" rule in the one case that rule exists for. The same bare `JSONDecoder` also failed the row model outright (`typeMismatch(Double)` on `updated_at`), which would have broken the iOS drafts list on first load. Every iOS test passed throughout, because they encoded with the same formatter they decoded with.
- **Decision:** Two standing rules. **(1)** Any data shape shared by more than one client is tested on each surface against **real payloads produced by the others**, verbatim — including precision variants and explicit nulls — never against that surface's own output. Where the shape crosses the database, a committed end-to-end harness is the proof: `packages/supabase/scripts/verify-pebble-drafts.ts` is the pattern (anon key only, signs up throwaway users and tears them down through the real `delete-account` function, so anyone who can run the app can run it). **(2)** Timestamps crossing a surface boundary are parsed **tolerantly** and emitted at the **narrowest** precision every reader accepts. On iOS that is `ISO8601Flexible` — fractional-then-whole on the way in, whole seconds on the way out (matching `PebbleCreatePayload` byte-for-byte, so publish is unchanged). A model never leaves a timestamp to whatever date strategy the ambient decoder happens to carry; it decodes from the string form explicitly.
- **Why:** The failure was invisible to the only tests that existed, and silent at runtime — no error, no log, just the wrong time on a published pebble. Same-surface round-trips are structurally incapable of catching a same-surface formatter bug, so the test strategy, not the formatter, was the root cause. Emitting the narrowest precision rather than the richest means the strictest reader still parses it, which is the direction that fails safe when a fourth surface or an older build appears. And a model that depends on its decoder's configuration breaks the day the SDK changes that default, silently, in a way no compiler catches.
- **Consequences:** Android needed no code change (`OffsetDateTime.parse` accepts all three precisions) but gets the same foreign-payload tests anyway, because "it happens to work" is not a contract. Anything comparing values that have been through Postgres `jsonb` must compare **canonically** — jsonb preserves key order at no depth, and a naive `JSON.stringify` equality reports an intact payload as changed (this cost two false failures in the harness before the assertion was fixed rather than the product). When the draft payload gains a key, add it to that harness's `iosShaped` fixture. Candidate for promotion into `CLAUDE.md` at the next monorepo-audit grooming pass; until then it lives in the M47 design's D12 + "Lessons learned".
- **Supersedes / Superseded-by:** Extends 2026-07-29 "Drafts: a separate jsonb table…" (#639) with the contract-testing rule that milestone lacked.
- **Refs:** #651, #652, `docs/superpowers/specs/2026-07-29-drafts-and-autosave-design.md` (D12, "Lessons learned"), `apps/ios/Pebbles/Features/Path/Models/ISO8601Flexible.swift`, `packages/supabase/scripts/verify-pebble-drafts.ts`.

## 2026-07-30 — Achievements: a client-called idempotent RPC, permanent badges, karma per badge via `grant` at unlock (#664)

- **Status:** taken
- **Scope:** db, api, core
- **Context:** M48 ships the achievements backend. The eight badge families span six tables (`pebbles`, `pebble_domains`, `collections`, `souls`, `glyphs`, `glyph_entitlements`), the repo has no cron/realtime infrastructure, `create_pebble`'s `returns uuid` is a three-surface wire contract, and web glyph carving is a direct client insert with no RPC seam — so every trigger/cron/piggyback design collapses on contact. Meanwhile the roadmap (§5 item 5) had parked achievement karma as "deferred", but the admin-library and rewarding-screen satellites arrived before the first issue was cut, forcing the karma question now.
- **Decision:** Evaluation is **one client-callable idempotent `security definer` RPC**, `check_achievements() returns table (slug, karma_granted)`: a stats CTE computes each family's count once, a single `insert … select … on conflict do nothing` against the `achievement_unlocks` PK `(user_id, achievement_id)` records the new unlocks, and a chained CTE emits one `karma_events` row per newly unlocked badge with `karma_reward > 0` — `reason = 'grant'` (reserved since `20260629192621`, emitted nowhere else), `type = 'credit'`, `delta = karma_reward` read at unlock time, `ref_id` = the achievement id. **No triggers, no cron, `create_pebble` untouched**; clients fire the RPC after count-changing mutations and on screen open, and the screen-open call *is* the retroactive grant. `achievement_unlocks` is write-locked on the `wallet_balances` precedent (owner-only SELECT, no write policies) and **badges are permanent** — no revocation path, count regressions are harmless. The catalog is a seeded reference table with deterministic `md5('achievements:<slug>')::uuid` ids; the per-emotion/per-domain rows are generated by `sync_achievement_catalog()` (service-role only), the drift guard against the live reference tables.
- **Why:** The unlocks PK makes both the unlock and its karma exactly-once with zero bookkeeping — a re-run inserts nothing so it pays nothing, which also makes failed fire-and-forget calls self-healing. Returning what was actually emitted (not the catalog's current value) means the rewarding screen can never display a number the ledger doesn't hold. Karma default 0 ships the *rail* without changing the economy: "cosmetic" is just the default value, and the maintainer prices badges in the admin later.
- **Consequences:** **Standing rule:** any future migration or admin add-RPC that inserts an emotion or a domain re-runs `sync_achievement_catalog()` in the same transaction. `karma_reward` edits apply to future unlocks only — never re-emit, never retro-pay. Retirement is `is_active = false` (stops future unlocks and their karma; emitted events and existing unlocks stay), never a delete. Per the M46 standing rule, `achievement_unlocks` is appended at `purge_account`'s section-(4) marker and to `verify-account-purge.ts`; the catalog itself is global reference data untouched by purge, and badge glyphs (always system-owned, `user_id = null`) need no kept-glyph-predicate extension.
- **Supersedes / Superseded-by:** Supersedes the roadmap §5 item 5 "achievement karma deferred" stance — the karma rail ships in the core migration with default 0, per the design doc.
- **Refs:** #664, `docs/superpowers/specs/2026-07-29-achievements-design.md` (D1–D6, D9, D10), `packages/supabase/supabase/migrations/20260730090000_achievements.sql`, `packages/supabase/scripts/verify-account-purge.ts`, roadmap §M48 + §5 item 5.

## 2026-07-30 — Cross-user reads are definer-RPC projections; `profiles` RLS is never widened (#654)

- **Status:** taken
- **Scope:** db, core, auth
- **Context:** M50 ships the first read of one user's data by another (and by anonymous visitors): the public profile. `profiles` carries columns that must never cross users (`is_admin`, consent timestamps, quota columns), and the M45 audit showed how easily wide grants leak (#616). The roadmap (§5 item 8) prescribed the pattern; M50 is its first instance.
- **Decision:** Cross-user reads go through `security definer` RPC **projections** that build an explicit jsonb of allowed fields — never through widened RLS on `profiles`, `glyphs`, or enrichment tables, and never through new views. `get_public_profile(p_handle)` is the template: definer + `stable` + `set search_path = public`, explicit `revoke all … from public` then `grant execute` to exactly the roles that need it (here `anon, authenticated`), null for unknown *and* known-but-private targets (enumeration resistance), and engagement recomputed internally for the target user rather than un-scoping `v_ripple` / `v_bounce` / `get_profile_engagement`.
- **Why:** A projection makes the exposed field list a reviewable allowlist in one place. Widening RLS exposes whole rows to PostgREST's column selection, so every future column addition would silently join the public surface. Recomputing engagement internally keeps the owner-scoped views/RPCs untouched and lets the public variant differ deliberately (UTC bucketing, no raw counts, no `active_today`).
- **Consequences:** M49 (connections), M51 (shared pebbles), and M53 (pairs) must each mint their own projection RPCs with their own allowlists — do not reuse `get_public_profile` for authenticated-only surfaces by adding fields to it, and do not return `user_id` from any public projection. M48 extends `get_public_profile`'s `achievements` key in place (the key ships empty from day one, so clients need no contract change).

- **Refs:** #654, `docs/superpowers/specs/2026-07-29-public-profiles-design.md` (D4), `packages/supabase/supabase/migrations/20260730120000_public_profiles.sql`, roadmap §M50 + §5 item 8.

## 2026-07-30 — Handle policy: lowercase 3–30 `[a-z0-9_]`, trigger-enforced reserved list, freed on deletion, no history (#654)

- **Status:** taken
- **Scope:** db, core
- **Context:** M50 introduces `profiles.handle`, the public URL identity (`/u/<handle>`). Its rules have to hold against every write path — `profiles_update` RLS lets owners write columns directly, so RPC-side validation alone is bypassable.
- **Decision:** Handles are stored normalized (lowercase), 3–30 chars of `[a-z0-9_]`, starting and ending alphanumeric, enforced by a CHECK constraint; `public_profile = true` requires a handle (CHECK); uniqueness (and the claim race) is settled by a unique index; the reserved list lives in `reserved_handles`, is admin-extensible without a migration (is_admin-gated insert/delete), and binds direct writes via a `before insert or update of handle` trigger. `set_handle` is the sanctioned path and maps failures to stable codes (`invalid_handle` / `handle_reserved` / `handle_taken`); `set_handle(null)` releases the handle and drops the public flag in the same statement. A released or purged handle is immediately claimable by others: no handle history, no redirects — public share links simply break.
- **Why:** Structural constraints make invalid states unrepresentable instead of policed by convention; the trigger closes the direct-write hole a table-local CHECK cannot (it needs a cross-table lookup). No-history is deliberate product simplicity — a handle is a pointer, not an archive.
- **Consequences:** `purge_account` needs no M50 extension (the `profiles`-row delete frees the handle; `reserved_handles` is admin data) — verified by the purge harness. Impersonation risk from handle recycling is accepted at this scale and mitigated by the reserved list; revisit if abuse appears (M56 adds reporting).

## 2026-07-30 — Connections: single-row symmetric, invite/QR only, no search; blocks from day one (#658)

- **Status:** taken
- **Scope:** db, core, webapp, ios, android
- **Context:** M49 introduces the schema's first user↔user primitive on a graph where every user table is RLS'd to `user_id = auth.uid()` and `profiles` is owner-only; it sits on the critical path (M45 → M49 → M53 → M56 → M57) gating the M51 `private` tier, M52 seaming, M53 pairs and the M56 UGC batch, Apple's UGC guidelines require blocking at launch, and the roadmap pre-constrains discovery to invite/QR only with symmetric consent — no search, no directory.
- **Decision:** We will model a connection as **one ordered row** (`check (user_a < user_b)`, `unique (user_a, user_b)`, **no status column** — accepting the invite *is* the mutual consent, and the invite table is the pending state), written only by `security definer` RPCs that return display projections (`display_name` + glyph `strokes`/`view_box`), never a `profiles` row; the multi-use invite is a **plaintext 32-byte base64url token stored for re-display** (a 7-day revocable capability, not a credential), `create_connection_invite` **returns the live invite instead of reissuing** (`p_rotate := true` is the entire revocation surface), a fifth RPC `preview_connection_invite` is **granted to `anon`** (token possession = capability, so the sign-up-first `/invite/[token]` page renders "who invites you" without an account), the accept-time **block check runs in either direction and surfaces as `invite_expired`** (a block is never revealed to either party), blocks ship day one as one directed row (the remover blocks the removed), and the only link format is the canonical **`https://www.pbbls.app/invite/<token>`** URL via universal/App Links with **no custom scheme**.
- **Why:** The ordered pair plus `on conflict do nothing` gives structural idempotency for free (re-scans and retries of a dinner-table QR are the *normal* case) where mirrored rows or a status column would mean double-entry bookkeeping and derivable-state drift; hashing the token breaks the "re-open the invite screen and show the same QR" model and forces three clients to persist plaintext copies, while return-the-live-one keeps yesterday's pasted link alive; the either-direction check stops the blocker reconnecting through the blocked user's invite and also retroactively defends the remover's still-live invite with zero invite mutation; the anon preview reveals exactly what the accepter would learn seconds after accepting, and widening `profiles` RLS instead is banned; the https URL is its own fallback (a not-installed user lands on the working web accept page, where a custom scheme browser-errors) and one URL serves link, QR and web at once.
- **Consequences:** **M52/M53 extend `remove_connection` at its in-body `>>> M52/M53: sever seams and pairs <<<` marker, in the same transaction** — the purge_account append-marker pattern applied to a function body; **block management UI is deferred to M56**, so until then an accidental block is recoverable only by a service-role row delete. `purge_account` gains three deletes at the section-(4) marker, two of them deliberately two-sided (`p_user_id in (user_a, user_b)` / `(blocker_id, blocked_id)`) — do not "simplify" them to a single column. Connections emit zero karma structurally (no new reason on the `karma_events` CHECK). No push, no realtime: accepted connections surface on next app open.

## 2026-07-31 — Two migrations re-emitting one function off the same base silently drop each other's appends (#687)

- **Status:** taken
- **Scope:** db
- **Context:** M48 (achievements) and M49 (mutual connections) both landed on `main` within hours, and each re-emitted `purge_account` with its own append at the section-(4) marker — the pattern the M46 standing rule prescribes. Neither branch saw the other's copy, and both were `create or replace` of the whole body. By timestamp the M48 copy (`20260730090000`) applies after the M49 one (`20260730070347`), so the merged history's final definition carried `achievement_unlocks` and had silently lost `connections`, `connection_invites` and `connection_blocks`. Both branches were green: each replayed cleanly on its own, the collision only exists in the merged order. Caught during the #687 apply, before either migration reached the linked project.
- **Decision:** The append-marker convention is kept, but it is **not** collision-safe on its own. When two open branches both re-emit the same whole-body function, the merge is a **manual union** — re-emit once more in a new migration with both appends — and the standing rule now extends to the harness: a table added to `purge_account` must gain its seed **and** its zero-row assertion in `packages/supabase/scripts/verify-account-purge.ts` in the same change. That harness is what turns the collision from silent into loud.
- **Why:** `create or replace function` has no merge semantics — the last writer wins the entire body, and git reports no conflict because the two migrations are different files. Timestamp ordering makes the loser arbitrary (whichever branch merged *first* is the one that gets clobbered), so review of either PR in isolation cannot catch it. The verify harness already asserted both M48's and M49's tables, so it would have failed on the merged schema; nothing ran it between the merges.
- **Consequences:** M52/M53 append to both `purge_account` and `remove_connection` (per the M49 entry's in-body marker) and are the next likely collision. Before applying any batch of migrations that includes more than one re-emission of the same function, diff the bodies pairwise and union them. Run `verify-account-purge.ts` against the linked project after any batch that touches `purge_account`, not just after a single PR.

## 2026-08-24 — Android gets the valence fan; the mesh is baked to a bitmap and the roll buzzes through the model only (#729)

- **Status:** taken
- **Scope:** ui, android
- **Context:** #725 shipped the Android record flow but kept the nine-tile valence grid, recording that mirroring iOS's fan (#727/#728) was a follow-up. #729 is that follow-up's Android half. Three things did not port mechanically. SwiftUI's `MeshGradient` — which the highlight stone's wash, its ink and its selected wash all are — has no Compose equivalent at all, not even the iOS-17 linear fallback's justification (Compose has no mesh primitive to guard against). iOS's `ValenceRollView` plays `TapHaptics.selection` at each detent *and* its record step buzzes again through `RecordFlowModel`, which on Android would be two buzzes for one detent against the flow's explicit one-tap-one-buzz rule. - **Decision:** **The three gradients are baked, not drawn.** `ValenceMesh` resamples the 4×4 control grid — the same sixteen sampled hexes and the same off-grid control points as iOS — onto a 64² pixel square by Shepard inverse-distance weighting, which a `BitmapShader` then stretches with linear filtering. **The roll plays no haptic of its own**: the record step's detents buzz through `RecordFlowModel.selectValence`, and the edit sheet (which has no model) buzzes in its own `onChange`. **The fan scales to fit** rather than being fixed: `BoxWithConstraints` reports a bounded width even inside a vertical scroll, so the constant that iOS could not derive safely, Compose can. - **Why:** On the mesh: a bilinear resample would have to ignore the control points' off-grid displacement, which is the one thing making the gradient wander rather than band; Shepard weighting is exact at each control point and smooth between, and `ValenceMeshTest` pins down the property that actually matters — every baked pixel stays inside the 3°–41° warm band the reference was chosen for. On the haptic: the flow's rule is structural on Android ("a tap that does not call a model method changes nothing, and every method there buzzes"), so duplicating iOS's view-level buzz would break the rule the port exists to keep. On the wobble flag: promoting it to unconditionally `true` the way iOS did in #727 would close the #555 experiment across every Android surface and orphan the `WOBBLE_ENABLED` plumbing in `build.gradle.kts` and `android-release.yml` — a decision worth its own change, not a side effect of this one.
- **Consequences:** **The valence step no longer advances on tap on Android either** — it commits in place and `Continue` advances, which is the D3 exception #725 said not to add without the fan, and `ValencePickerSheet` now stages and commits on **Done** (a roll that dismissed on change would close on the first swipe). `RecordStep.VALENCE.bringsOwnScroll` is now false: the fan is fixed-height content, and the scaffold's own scroll is what carries it on a short screen — the roll's vertical drag wins because `detectDragGestures` consumes. **A local release build without `WOBBLE_ENABLED` now renders wobbled stones in the picker and smooth ones on the Path**; every shipped build sets the flag, so this is only visible to forks and to local release builds. The nine `res/raw/valence_art_*.svg` artworks are a **third** copy of iOS assets under the rename-on-copy rule (after the outlines and the Rive files) and must not be re-derived from the web line art — `ValenceArtTest` fails if one stops carrying exactly one filled path. **No schema, RPC or payload changed**; `positiveness` (-1/0/+1) and `intensity` (1/2/3) are what they always were, so web can still land its half of #729 in any order.

## 2026-09-02 — Privileged profile columns are pinned by trigger; owning a row is not authority to raise capability in it (#739)

- **Status:** taken
- **Scope:** db, supabase
- **Context:** `profiles_update` has been `for update using (user_id = auth.uid())` since `20260411000001_core_tables.sql`, with no `with check` and no column scoping. That scope is right for the columns a user owns and wrong for four that grant capability: `is_admin` (the sole input to `is_admin(uuid)`, which gates every admin RPC, all analytics RPCs, lab-assets storage writes and unpublished-logs reads), `max_media_per_pebble` (the server-side media quota), and `terms_accepted_at` / `privacy_accepted_at` (consent proof kept for GDPR accountability). Because the helper reads only that one column, an owner-scoped update of it was an owner-scoped grant of operator rights. The repo had already fixed this class twice by narrowing *read* authority (#442 `v_ripple`, #616 `v_pebbles_full`), and `20260730120000` gave `handle` CHECK constraints plus a dedicated `before update of handle` trigger for exactly this reason — "`profiles_update` RLS lets owners write columns directly" — but the write-side capability columns never got the same pass. Found by Kritik audit `2026-08` as `F-2026-08-SEC-supabase-01`, that audit's only open P0.
- **Decision:** A `before update of is_admin, max_media_per_pebble, terms_accepted_at, privacy_accepted_at` row trigger (`enforce_profile_privileged_columns`, `20260902090000`) raises `profiles_privileged_column` when any of the four changes and `current_user` is `authenticated` or `anon`. `postgres`, `service_role` and any `security definer` function pass through, which makes the RPC the sanctioned mutation seam. The policy also gains an explicit `with check (user_id = auth.uid())`. The function is `security invoker`, unlike `enforce_reserved_handle`.
- **Why:** Not column privileges: Supabase grants table-level `UPDATE` to `authenticated` and a table grant covers every column, so moving to per-column grants would mean re-granting on every future `ALTER TABLE` — a silent hole the first time someone forgets. A `CHECK` constraint cannot see `OLD`, so it cannot express "unchanged". `security invoker` because the function reads nothing and needs no elevation, and because `current_user` must stay the role that actually issued the statement or the exemption means nothing. The `of <columns>` clause keeps the trigger off the hot path, and the inner `is distinct from` means a client that echoes back an unchanged value is not broken.
- **Consequences:** **A new `profiles` column that gates access must be added to the trigger's column list AND to `PINNED` in `packages/supabase/scripts/verify-profiles-privileged-guard.ts` in the same change** — a privileged column absent from both is writable by every authenticated user, which is the whole of this bug. Granting an admin, raising a quota or backfilling consent now requires the service role, a `security definer` RPC, or the dashboard; the admin bootstrap in `apps/admin/README.md` is unaffected because it runs as `postgres`. `handle_new_user()` writes the consent timestamps as a `security definer` trigger and is likewise unaffected. Do not "fix" a blocked update by dropping the trigger. The harness is not in CI: it signs up a throwaway user against the linked project, and no `verify-*` harness runs in CI today — wiring one in is a separate decision about production writes on every PR.
- **Supersedes / Superseded-by:** Extends the read-authority narrowing of #442 and #616 to the write side, and generalizes the single-column `handle` guard of `20260730120000` to the capability columns.
- **Refs:** #739, `F-2026-08-SEC-supabase-01`, `packages/supabase/supabase/migrations/20260902090000_profiles_privileged_guard.sql`, `packages/supabase/scripts/verify-profiles-privileged-guard.ts`.

## 2026-09-02 — The four anon contract harnesses become a CI gate; the purge harness stays manual because the service-role key stays out of a public repo (#741)

- **Status:** taken
- **Scope:** supabase, db
- **Context:** `packages/supabase/**` had no CI coverage at all. `android.yml` triggers on `apps/android/**` and `arkaik.yml` on `docs/arkaik/**`; a PR changing only migrations or edge functions got two Vercel builds proving the web and admin apps still compile, which they would with or without any schema change. Meanwhile the five `verify-*` harnesses — the actual proof for anything crossing a surface boundary — ran only when a human remembered to. #739 is what that costs: a privilege-escalation gap sat in `profiles_update` from `20260411000001` until an audit found it, and the guard that closed it (#740) was protected by nothing but a script somebody had to think to run. The obstacle is that these harnesses are acceptance tests, not simulations: they sign up throwaway users against the **linked production project** and delete them through the real `delete-account` edge function, so any CI trigger is a production write.
- **Decision:** A `supabase.yml` workflow runs the **four anon-only harnesses** (`drafts`, `visibility`, `public-profile`, `guard`) on same-repo `pull_request`s touching `packages/supabase/**`, **nightly** against `main`, and on `workflow_dispatch`. Fork PRs **skip** the job (`head.repo.full_name == github.repository`) rather than failing it. `verify-account-purge.ts` is **not** in CI: it is the one harness needing `SUPABASE_SERVICE_ROLE_KEY`, that secret is **not added to this public repo**, and the harness stays a manual run. Each harness is a separate step calling a new `db:verify:*` npm script, so CI and a human invoke exactly the same command.
- **Why:** On the trigger: nightly alone detects a dropped guard *after* merge, which is the #739 failure mode again; the path-filtered PR trigger blocks it, and the nightly still catches the case nobody path-matched. On the fork gate: `pull_request` from a fork gets no secrets, so the harnesses would fail with `SUPABASE_URL and SUPABASE_ANON_KEY must be set` on every outside contribution — and `pull_request_target` is the wrong fix, since it would hand repository secrets to fork-authored code. On the service role: a leaked service-role key is total database access, and a same-repo PR is still code that runs before review, so the purge contract keeps the human gate it already has rather than trading it for a new class of exposure. On concurrency: grouping by ref with `cancel-in-progress: false` means a run is never killed between signup and its `finally` (which would orphan an account), while runs from different refs may overlap — every harness namespaces its users by a per-run uuid and asserts only on rows its own user owns.
- **Consequences:** **Dropping `profiles_privileged_guard`, breaking a grade RLS policy, widening the `get_public_profile` allowlist or regressing the draft lifecycle now fails a PR check**, and surfaces within a day even on a PR that never touched `packages/supabase/`. Every merged PR touching that path now performs a handful of production signups and deletions; that is the price of the harnesses being proof rather than simulation. **`purge_account` remains the one contract with no automated gate** — the standing rule to run `npm run db:verify:purge` after any batch touching it is now the *only* thing protecting it, and is correspondingly less forgiving. A run cancelled by hand can still orphan a throwaway account; they are greppable by the `drafts-verify-` / `grades-verify-` / `public-verify-` / `guard-verify-` prefixes on `@example.test`, and there is no automated sweep because deleting them needs the service role. A future harness added to `scripts/` gains a `db:verify:*` script and a workflow step in the same change, or it is not a gate.
- **Supersedes / Superseded-by:** Supersedes the "The harness is not in CI … wiring one in is a separate decision about production writes on every PR" note in the 2026-09-02 entry for #739 — that decision is now taken. The rest of that entry stands.

## 2026-09-02 — The nightly harness run logs a result table and opens one reused tracking issue; a failing PR run still opens nothing (#743)

- **Status:** taken
- **Scope:** supabase, infra
- **Context:** #741 wired the four anon contract harnesses into CI and recorded that a red nightly would "open nothing (a notification is enough to start)". That notification ends in exactly one place: GitHub's default email/web notification to whoever last modified the cron syntax, plus a red run in the Actions tab. This repo has no other failure wiring — no workflow contains `failure()`, no issue-opening step, no webhook. So the nightly, the one gate that catches a regression on a PR that never touched `packages/supabase/`, was also the one gate whose failure nobody is forced to walk past. Kritik was considered as the destination and does not fit **yet**: the `kritik_*` tools refuse in hosted mode, they run against a checkout's `docs/quality/` files, and this repo has none. That is a dated limitation, not a verdict — `alexisbohns/arkaik#400` is the design ground for giving a hosted project an agent read/write path to its quality state, and its cheapest candidate write mechanism (append `quality.*` events, re-derive on read, already proven by the GitHub App webhook) is exactly the shape a nightly failure needs. Kritik's own vocabulary fits too: a tripped signal is "the prompt to go look — cheap, frequent, and allowed to be wrong", which is what a red harness is, where a finding is expensive and rare. The `quality_signals` view and the admin's `QualitySignalsTable` are product analytics (retention, pebbles per WAU), not engineering signals.
- **Decision:** Every run writes a per-harness table (harness, result, assertion counts) to the job summary — each harness step appends a row to a ledger through `.github/scripts/verify-harness.sh`, and **one** later step turns the ledger into the table — and a **scheduled** failure opens one issue titled `[Bug] Nightly contract harnesses are failing`, commenting on it if it is already open. A **PR** failure opens nothing. The issue is closed by hand, never automatically by a subsequent green run.
- **Why:** One reused issue means a contract broken for a week is one thread rather than seven, and it lands somewhere with labels and a milestone instead of an inbox. A PR failure needs no issue because the red check is already in front of the person who caused it. Auto-closing on a green run was rejected: an intermittent failure would quietly close its own report, which is the failure mode the whole gate exists to prevent. The wrapper script exists for one specific reason: the summary needs the harness's stdout, GitHub's default shell is `bash -e {0}` with **no `pipefail`**, and `harness | tee` under that shell exits 0 for a failing harness — so the wrapper reads `PIPESTATUS[0]`, which is the harness's own status regardless of pipefail. The table is assembled by a single step for a second shell-level reason: `$GITHUB_STEP_SUMMARY` is a **per-step** file, so a table whose header and rows were written by five different steps would only render as a table if GitHub happened to concatenate those files without a blank line between them. One writer removes the bet.

Both migrations are generated from the JSON, so the JSON is the thing to edit; regenerating is a scripted step, not a hand edit. The two files are also the **only** off-database copy of this reference data, which is a backup the project did not previously have.

Both remain applied and unedited; their data step is now carried by the two migrations above.
- **Also recovered:** `public.sweep_orphan_snap_files` — a `security definer` function created in Studio for #322 and present in no migration, surfaced by the same `schema` job once the chain replayed far enough for the types diff to be meaningful. Every library here that reflects already ships rules inside its own artifact — Rive's `proguard.txt` is `-keep class app.rive.** { *; }`, broader than the `app.rive.runtime.kotlin.core.**` rule the issue proposed, so adding that rule would have been redundant, not protective; Ktor ships `META-INF/proguard/ktor.pro`, kotlinx-serialization ships full-mode rules under `META-INF/com.android.tools/r8/`, coroutines, Coil and OkHttp likewise. supabase-kt ships no rules **and needs none**: its classes contain no `Class.forName`, `getDeclaredClasses`, `newInstance` or `ServiceLoader`, and its models are `@Serializable`, which the serialization rules already cover. AndroidSVG and zxing reflect not at all. Writing rules for them anyway is the standard way a keep radius quietly grows until minification stops paying. The **gate is `bundleRelease`, not `lint`,** because lint cannot see a broken keep rule — only actually running R8 and `lintVitalRelease` can, and running them unsigned costs one build step and no release machinery. `NewerVersionAvailable` is the one lint check disabled outright: it resolves the latest published version over the network, so every upstream release becomes a finding no committed baseline can hold, and Dependabot already owns bumps here.
- **Consequences:** The AAB drops from 25.3 MB to 20.7 MB and from **3 DEX files / 37.3 MB to 1 / 6.1 MB (-84%)**; resource entries go 113 → 72. The 2026-07-14 claim above now holds as written. `apps/android/app/lint-baseline.xml` is committed with **60 accepted findings** (13 `PluralsCandidate`, 9 `NonObservableLocale`, 8 `UnusedResources`, 7 `MissingQuantity`, 6 `UseKtx`, and a tail) — those are debt tracked in their own issues, not a clean bill of health, and the baseline must be regenerated (`./gradlew updateLintBaseline`) whenever one is deliberately accepted, never to make a new finding go away. **Stack traces from Play are now obfuscated**; they are only readable because the mapping file reaches the Console, so a release run whose publish step is skipped keeps its mapping as an artifact. Every future dependency that reflects is now a runtime crash rather than a build failure — the pre-merge `bundleRelease` catches missing-class and keep-rule *configuration* errors, not reflection that R8 silently strips, so a minified smoke pass stays a manual step on any PR adding a library.

## 2026-09-18 — `glyphs.strokes` is a CHECK-constrained shape, written as inline jsonpath rather than a helper function (#870)

- **Status:** taken
- **Scope:** db, supabase
- **Context:** `public.glyphs.strokes` is `jsonb not null default '[]'` with no constraint, writable by its owner straight through PostgREST and by five `security definer` RPCs (`create_pebble`, `update_pebble`, `publish_admin_glyph`, `admin_set_domain_glyph`, `admin_set_achievement_glyph`). Every reader requires the same two keys — android `GlyphStroke.kt` and ios `GlyphStroke.swift` declare `d`/`width` non-optional, web's `MarkStroke` the same, and the edge compositor re-emits against that pair since #829 — but nothing enforced it, so the agreement was a convention four codebases happened to share. `verify-account-purge.ts` seeded fixture glyphs as `[{"points": [...]}]`; `purge_account` anonymized the sold one to `user_id = null` (deliberate — buyers hold entitlements), which is the definition of a **system glyph**; and Android, the only surface that lists those (M43 design D7, a named deviation from iOS's `eq(user_id, me)`), decodes the whole result set before filtering. Six rows had accumulated at one per manual harness run, and `decodeList` being all-or-nothing meant the glyph picker and Profile → Glyphs were dead for **every** Android user, new accounts included. iOS and web were never affected: both filter to the caller's own rows server-side, and `v_glyph_market` requires `listed`, which the purge clears.
- **Decision:** `glyphs_strokes_shape` — `jsonb_typeof(strokes) = 'array'` and no element failing `!exists(@.d) || !exists(@.width) || @.d.type() != "string" || @.width.type() != "number"`, written as an **inline `jsonb_path_exists` call, not a helper function**. An empty array stays valid (a blank glyph is real — the default system glyph is `'[]'`), and extra keys are tolerated. The six offending rows are deleted in the same migration, scoped to `user_id is null`. The harness seeds `{d, width}`, asserts the kept glyph still *decodes* rather than merely counting it, and removes the surviving sold glyph in teardown.
- **Why:** The constraint is inline because **a CHECK that calls a function is evaluated with the inserting role's privileges** — verified locally: with `EXECUTE` revoked from `PUBLIC`, every insert into the table fails `permission denied for function`, including the valid ones. A helper reads better and would have been the obvious refactor; it also means a routine `revoke execute on all functions in schema public` takes glyph creation down across four clients, with an error message pointing at privileges rather than at the constraint. Built-ins carry no such dependency. It is a CHECK and not a trigger because the property is about the value alone. The delete is scoped to ownerless rows so a migration can never silently remove a user's drawing — a malformed owned row fails the `ALTER` loudly instead, which is the right way to find out — and FK protection does the rest: `souls.glyph_id` is `ON DELETE RESTRICT`, `pebbles`/`domains`/`achievements` are NO ACTION, so a glyph anyone actually uses raises an FK error rather than disappearing. Client-side per-row decoding was considered and deliberately **not** taken here: it is a behaviour change that would have to land on three surfaces or none, and with the column constrained it guards against a row that can no longer exist.
- **Consequences:** **Any future stroke attribute may be added freely, but `d` and `width` can never be dropped or renamed without a migration that moves this constraint first** — it is now the schema-level statement of the cross-surface glyph contract, and the four client models are downstream of it rather than beside it. The five RPCs that insert glyphs from caller-supplied jsonb now surface `23514` instead of writing an undecodable row; none of them handle that code specifically, so a malformed payload becomes a raw Postgres error in the client's error path rather than a silent success. Verified against the linked project's 133 rows on a local Postgres 16 before pushing — exactly the 6 failed, the `ALTER` succeeded over the remaining 127, and the fixture shape was rejected including from an unprivileged role. **Android's picker was fixed by the data deletion, not by the constraint**; the constraint is what stops the next one. The deeper defect the fixtures exposed — a purged seller's *paid* glyph becoming a free system glyph, because `can_use_glyph` reads `user_id is null` as first-party — is untouched here and tracked as #872.
- **Supersedes / Superseded-by:** Extends the 2026-08 hardening of the compositor (#829/#830), which re-emits `d` from the path grammar rather than trusting it. That work made the *server* safe against this column; this makes the column safe.
- **Refs:** #870, #872, #829, `packages/supabase/supabase/migrations/20260918200000_glyph_strokes_contract.sql`, `packages/supabase/scripts/verify-account-purge.ts`, `apps/android/app/src/main/kotlin/app/pbbls/android/features/glyph/services/GlyphMarketService.kt`.

## 2026-09-19 — System glyphs are a marked column, not an inferred null owner; anonymized glyphs stop being commons (#872)

- **Status:** taken
- **Scope:** db, supabase, android, core
- **Context:** `user_id is null` carried two incompatible meanings. **(a)** First-party seed — the default glyph, the 18 `domain:<slug>` seeds, and the rows `admin_set_domain_glyph` / `admin_set_achievement_glyph` mint. **(b)** A glyph whose creator deleted their account, which `purge_account` deliberately keeps and anonymizes because buyers hold entitlements on it. `can_use_glyph` and `glyphs_select` both read (a) and therefore accepted (b). The 2026-07-29 entry below saw this and **accepted it on purpose** — "`user_id = null` is already readable and usable by everyone … so buyers keep rendering with zero schema surface added", consequence "anonymized glyphs become de-facto commons (usable by all) — accepted". What that framing missed is that the commons is *paid third-party artwork*, that it is indistinguishable from a curated first-party seed, and that it grows the system set with work the admin moderation queue never saw. Android — the only surface listing system glyphs (M43 D7, a named deviation from iOS/web's `eq(user_id, me)`) — served it free in every user's Mine tab and picker. Buyers' entitlements survived and simply stopped meaning anything. Found while fixing #870; that entry names this as untouched and tracked here.
- **Decision:** `glyphs.is_system boolean not null default false`, backfilled `true` for `user_id is null and no glyph_submissions row and no glyph_entitlements row`. `can_use_glyph` and the `glyphs_select` policy swap their `user_id is null` arm for `is_system`. `enforce_glyph_system_flag`, a `before insert or update` trigger, rejects any change to the flag unless `auth.uid()` is null (migrations, service role) or `is_admin`. `admin_set_domain_glyph` and `admin_set_achievement_glyph` stamp `is_system => true` on their first-glyph insert; `publish_admin_glyph` deliberately does not, because it writes `user_id = v_user` and its output is sold through `buy_glyph` like any other listing.
- **Why:** A **stored marker** over the two alternatives. Deriving it (`user_id is null and never submitted`) needs no migration and no backfill, but encodes "system" as "never listed" — a coincidence of today's data, not a fact about the row — and the predicate would have to be repeated in four places including a Kotlin client that would need an extra embed to evaluate it. A **sentinel retired-creator user** keeps every existing reader correct untouched, but means a real `auth.users` row that must never log in, and `buy_glyph` would credit karma to it on any future sale. The **backfill's two `not exists` clauses** are what make it correct at apply time rather than only at authoring time: every sold glyph carries an approved submission by construction (`buy_glyph` requires `status = 'approved' and listed`; `purge_account` keeps the row and flips only `listed`), so a seller purging between authoring and deploy is excluded automatically. It is a **trigger, not a column-level `REVOKE`**, because Postgres cannot revoke one column out of a table-level grant — that route would mean revoking table `INSERT`/`UPDATE` and re-granting every other column by name, a list that rots as columns are added. The guard is load-bearing rather than theoretical: `glyphs_update` has no `WITH CHECK`, so Postgres reuses `USING`, and a self-promotion satisfies `user_id = auth.uid() and not submitted and not entitled`. The RLS swap is safe for the anonymized glyph **only** because `purge_account` preserves `status = 'approved'` and flips `listed` — the approved-submission arm still grants the read, so buyers' pebbles and souls keep rendering and the glyph stays browsable. Just the attach closes.
- **Consequences:** **`purge_account` needed no change at all** — it only nulls `user_id`, and the column defaults to `false`, so an anonymized sold glyph is non-system by construction rather than by a rule someone has to remember. **Ownerless no longer implies usable**, which makes any stray `user_id is null` row inert rather than free: `verify-account-purge.ts`'s own fixture picker was selecting its "system glyph" with `.is("user_id", null).limit(1)` and feeding it to a `souls` insert, which the `enforce_soul_glyph_usable` trigger would now reject — it selects on `is_system` instead. Probed before applying: 20 ownerless rows, all first-party (18 domain seeds, the default glyph, and one pre-marketplace row "Barking Dog" from 2026-04-23 that a soul and two pebbles already point at), none carrying a submission or entitlement, all 20 marked; 0 owned-but-system after. That last row is why the backfill is not a provenance allowlist over `domains`/`achievements` — it matches none of those and stripping it would have broken live references. **iOS and web are untouched and were never affected** (both filter `user_id = me`); Android is the only client changed, and D7 stays D7 — it still offers system glyphs, keyed on `is_system`. **`glyphs.is_custom` still drifts**: it is `generated always as (user_id is not null) stored`, so a purged creator's glyph still flips it false and the "% pebbles with a custom glyph" analytics metric still reclassifies bought artwork as system-seeded. Out of scope here because redefining a generated column means `DROP COLUMN` cascading into two analytics views and their RPCs; admin-facing only. **`profiles.glyph_id` remains unguarded** — `pebbles` is guarded through its RPCs and `souls` through its trigger, `profiles` through neither; pre-existing, neither widened nor narrowed by this change. A new CI-gated anon harness (`verify-glyph-usability.ts`, in `db:verify`) now asserts the guard on every push, including that the flag is not self-settable on insert *or* update — checked by the trigger's own error text plus a re-read, because an assertion that merely requires "some error" is green in the broken state too, which is the same shape of hole that let #872 ship.
- **Supersedes / Superseded-by:** Reverses the accepted consequence of **2026-07-29 — Account deletion: anonymize externally-referenced glyphs via the `user_id = null` system state (#631)**; that entry's purge ordering, predicate breadth and delisting are unchanged, but anonymized glyphs are no longer commons and its title's "system state" no longer holds. Amends **2026-06-30 — Glyphs become readable when listed/entitled (D8)**: the SELECT policy's second arm is now `is_system`, not `user_id is null`; the other three arms and the UPDATE/DELETE lock are unchanged, and the standing "do not narrow `glyphs_select` back to own-only" still applies. Closes the defect **2026-09-18 — `glyphs.strokes` is a CHECK-constrained shape (#870)** flagged as untouched.
- **Refs:** #872, #870, #631, #496, `packages/supabase/supabase/migrations/20260919090000_glyph_system_marker.sql`, `packages/supabase/scripts/verify-glyph-usability.ts`, `packages/supabase/scripts/verify-account-purge.ts`, `apps/android/app/src/main/kotlin/app/pbbls/android/features/glyph/services/GlyphService.kt`, `apps/android/app/src/main/kotlin/app/pbbls/android/features/glyph/services/GlyphMarketService.kt`, `docs/superpowers/specs/2026-09-19-glyph-system-marker-design.md`.

## 2026-09-19 — Services are the Android error boundary; conditions match `RestException.error`, not `Exception.message` (#850)

- **Status:** taken
- **Scope:** android, core
- **Context:** Platform and SDK exceptions crossed straight into UI code, and two things followed. **(a)** Raw SDK text was shown to users: `AuthScreen` and `WelcomeScreen` set `authError = e.message`, rendering whatever supabase-kt, Ktor or GoTrue put there — unlocalized, sometimes JSON, sometimes "Connection reset" — under the password field, against D9. **(b)** Domain errors were recovered by substring-matching that same text (`handleErrorStringRes`, `connectionsErrorMessage`, `glyphMarketErrorMessage`, `pebbleSaveErrorMessage`). The substring form is worse than it looks: `RestException` builds `Exception.message` as `error + "\n" + description + "\nURL: <request url>\nHeaders: <headers>\nHttp Method: …"`, so `e.message!!.contains("handle_taken")` was scanning the request URL and headers alongside the server's answer — a `not_found` reply to a URL containing the slug would have rendered as "that handle is taken".
- **Decision:** A sealed `DataError` (`Network`, `Unauthorized`, `NotFound`, `Conflict(code)`, `Quota`, `Unknown(cause)`) in `services/`, decoded at the service boundary by `Throwable.toDataError()`, which rethrows `CancellationException` first. Every feature's error→string mapping takes a `DataError` and returns a `@StringRes`; no `.message` read survives anywhere in `app/src/main`. Auth maps GoTrue's typed `AuthErrorCode` enum instead, with nine new en/fr strings.
- **Why:** supabase-kt already separates the server's own words into **`RestException.error`** — `PostgrestImpl.parseErrorResponse` passes the PostgREST body's `message` field there untouched — so the fix is to match that, exactly, rather than to search a blob. The conditions arrive as text because every one of them is raised as `raise exception 'handle_taken'`: the condition *is* the Postgres message and the SQLSTATE is `P0001` for all of them, so there is no second machine-readable field to prefer. That the payload is bare (no `ERROR:` prefix, no `(SQLSTATE …)` suffix — those are psql's rendering) was confirmed three ways: the supabase-kt source, PostgREST's documented body shape, and the web client, whose `.includes` matching is needed only because **web wraps the error itself** (`throw new Error(\`get_connections failed: ${error.message}\`)`) while Android's services do not wrap at all. `dataErrorOf(statusCode, error, sqlState)` is split out pure because constructing a real `RestException` needs a Ktor `HttpResponse`, and the part with judgement in it should be the part that is covered.
- **Consequences:** **Two behaviours improved rather than preserved.** A 401/403 now reads as a session problem instead of the generic line, and offline gets its own copy across every feature (`error_offline`). **One narrowing:** case variants no longer match (`"Already_Owned"` was a defensive guess in a test, never a value the server sends), and a condition embedded in surrounding text no longer matches — which is the point. **`handleErrorStringRes` changed signature** from `Throwable` to `DataError`, so its old test's synthetic `RuntimeException("...handle_taken...")` fixtures are gone; the fixtures are now the values PostgREST really sends. **The issue's literal acceptance grep (`grep -rn 'e.message' …/features`) can no longer return nothing**, because `.messageRes` — the `@StringRes` field the sealed UI states carry since #849 — matches it as a substring; the precise check is `grep -rnE '\.message\b'`, which returns nothing across all of `app/src/main`. **iOS and web still have the same bug** (`error.localizedDescription` and `.includes` respectively) and neither has per-code auth copy; Android is the first surface with a real mapping, so the three have deliberately diverged here until the other two follow. **Task item 2 of #850 — every service method returning a result type — is deliberately not done in one pass:** it touches the same eleven screens #849 has still to migrate, so each service adopts the result type in the same PR as its screen's ViewModel, which writes each ViewModel against the final error shape the first time instead of the second.
- **Supersedes / Superseded-by:** None. Hardens D9 (user-facing strings are resources) on Android.
- **Refs:** #850, #849, #848, `apps/android/app/src/main/kotlin/app/pbbls/android/services/DataError.kt`, `apps/android/app/src/main/kotlin/app/pbbls/android/features/auth/AuthErrorMessage.kt`, `apps/android/app/src/test/kotlin/app/pbbls/android/services/DataErrorTest.kt`.

## 2026-09-20 — Vercel skips builds for workspaces a push did not touch (#905)

- **Status:** taken
- **Scope:** facility, web, admin
- **Context:** Vercel Functions Storage for `pbbls` reached **4.3 GB** against 1.45 GB for melogram and 883 MB for arkaik, with the account at 8.27/10 GB — and the web app has no users, so this is not traffic. Functions Storage is `bundle size per deployment × retained deployments`, and two things multiply. **(a)** Neither `apps/web/vercel.json` nor `apps/admin/vercel.json` set an `ignoreCommand`, so Vercel's default applied: build on *every* push to the repo, whichever app changed. An **Android-only** PR produced a full `pbbls` **and** `pbbls-admin` deployment. The M61 Android stack (#852) pushing hard from Sep 10 lines up exactly with the curve climbing ~2.2 GB → ~4.5 GB: a navigation migration in `apps/android`, sharing no code with either deployed app, paying for two web deployments per push. **(b)** `apps/web/app/sw/[path]/route.ts` bundles the service worker *at request time* and picks its bundler at runtime (`useNativeEsbuild ? import("esbuild") : import("esbuild-wasm")`); on Linux that is the `esbuild-wasm` branch, and `node_modules/esbuild-wasm` is **14 MB**, which file-tracing pulls into that function's bundle on every deployment. Neither sibling project ships a runtime-bundled service worker.
- **Decision:** `"ignoreCommand": "npx turbo-ignore @pbbls/web"` in `apps/web/vercel.json`, and the `@pbbls/admin` equivalent in `apps/admin/vercel.json`. This addresses **(a)** only; **(b)** is left alone deliberately and tracked in #905.
- **Why:** `turbo-ignore` decides from the **workspace dependency graph**, not a path glob, which is what makes it correct rather than merely convenient — a path filter would have to be re-reasoned every time a workspace gains a dependency. Verified empirically against real commits on `main` before shipping, rather than assumed: an `apps/android`-only commit → web **skips**; an `apps/web` commit → web **builds**; a `packages/supabase`-only commit → web **skips** but admin **builds**, because `apps/admin` declares `@pbbls/supabase` and `apps/web` declares no workspace dependency at all. (The `packages/supabase` strings in `apps/web/lib` are comments mirroring SQL formulas, not imports.) An earlier round of this testing reported the opposite and was wrong: `turbo-ignore` compares `HEAD` against the ref, and the working tree had been left on an unrelated branch, so the diff under test was not the commit under test. Fixing (b) instead would be the larger win per deployment but is a behaviour change to the PWA, and fixing (a) is two lines with no runtime effect.
- **Consequences:** **A skipped Vercel build is now expected, not a failure** — anyone seeing "Ignoring the change" on an Android or migrations PR should leave it alone. **Watch the first Android-only PR after this lands**: if the Vercel check is a *required* status check, a skipped build may report differently (or not at all), and the branch protection rule may need adjusting — that is the one thing this change could disrupt, and it was not verifiable before merge. Storage already consumed is **not** reclaimed by this: that needs old preview deployments deleted in the console, which is a manual action. The 14 MB `esbuild-wasm` remains in every future web function bundle; this change reduces how *often* that is paid, not how much. **Both apps still rebuild on any root or lockfile change**, since those sit above every workspace in the graph.
- **Supersedes / Superseded-by:** None. First deployment-scoping decision for the Vercel projects.
- **Refs:** #905, #852, `apps/web/vercel.json`, `apps/admin/vercel.json`, `apps/web/app/sw/[path]/route.ts`.

That is a layout divergence only — no contract, token or behaviour moved. **Three files did not go where their folder suggested**: `VisibilityUi` (a `@DrawableRes`/`@StringRes` mapping that lived in a `models` package) went to `core/ui`, while `KarmaReason` and `AuthMode` went to `core/model` — the rule being that a presentation mapping which *detaches* from its type belongs in `core/ui`, and an enum carrying its own label in a constructor property is a domain type. **`core/model` is not quite pure Kotlin**: `EmotionPalette` holds parsed `androidx.compose.ui.graphics.Color` alongside its hex strings, so a real `:core:model` module would need `compose-ui-graphics` or a split — a decision for the day that module exists. **`ComposerMedia` stayed in `features/path`** although `di/ServiceBindings` binds it, because its implementation reaches into `features/path/valence`; moving it would have traded a harmless `di -> features` edge for the one edge the test forbids. **The boundary test is scoped to `main`**: a test driving one package's logic from another package's fixtures is not an architecture violation, and `AchievementsDecodingTest` is exactly that. **The Konsist artifact is `com.lemonappdev:konsist`**, not the `io.lemonappdev` the issue text names, which does not exist on Maven Central.
- **Supersedes / Superseded-by:** Supersedes the folder-layout section of `apps/android/CLAUDE.md` as it stood before this date, and narrows that file's opening "mirrors `apps/ios` 1:1" claim to behaviour, tokens and funnel rather than package structure. Does not amend any cross-surface contract.
- **Refs:** #851, #914, #852, `apps/android/app/src/test/kotlin/app/pbbls/android/architecture/ArchitectureBoundaryTest.kt`, `apps/android/CLAUDE.md`.

## 2026-09-24 — Android adopts the M3-evo Material 3 Expressive theme; D6 is superseded (#853)

- **Status:** taken
- **Scope:** android, ui
- **Context:** D6 made Material 3 a rendering engine only: no colour roles, typography or shapes in app code, with a partial bridge so stock components stopped rendering purple. The bridge left secondary/tertiary/error/containers at the M3 baseline, all five surface-container tiers equal to the ground (a dark sheet was `#171012` on `#171012`), no `Typography` (stock components rendered Roboto) and no `Shapes`, and the shared accent `#C07A7A` carried its near-white labels at 3.06:1. The maintainer produced a Material Theme Builder export (seed `#CE7E8A`) as the new Android brand.
- **Decision:** Android forgets the iOS-derived palette and type. The export's six schemes (light/dark × standard/medium/high contrast) are the theme, rooted in `MaterialExpressiveTheme` with `MotionScheme.expressive()`, the export's type (Inclusive Sans + Ysabeau, bundled variable fonts, M3 default scale, Expressive emphasized styles) and M3 Expressive shapes. App code reads `MaterialTheme.colorScheme/typography/shapes`; `PebblesTheme` keeps only `spacing` and the handwritten faces. **The error colour is amber** (`#7F560F` / `#F3BD6E`). **Wallpaper colour is on by default**, with a Settings switch. The system contrast level picks the scheme live on Android 14+. material3 is pinned to `1.5.0-alpha27`. The launcher icon is unchanged.
- **Why:** Stock components can only look like the brand if the brand is expressed in the theme they read, and #854 is about to replace every hand-rolled control with a stock one. A partial bridge guarantees leaks at every role it forgets. Amber over red: red read as aggressive; amber catches the eye without alarming. Wallpaper colour on by default is the platform's current expectation; the brand scheme remains the default for anyone who turns it off, and for every screenshot. alpha27 rather than 1.4.0 because 1.4.0 keeps the emphasized type getters, `MotionScheme.expressive()` and the increased shape steps internal; rather than alpha28+ because those pull Compose ui/foundation/runtime to `1.13.0-alpha01`.
- **Consequences:** **A third deliberate iOS divergence** (after the four-tab bar and the `core/` split): Android's palette, error colour and type no longer match iOS; #921 decides whether iOS follows. Emotion palettes and pebble renders are server data and unaffected; the pebble SVG accent (`primaryHex`) now follows `primary`, including wallpaper colour. **D5's DataStore trigger has fired** — `AppearancePreferences` is the first real user setting — but one boolean stays in SharedPreferences; #858 or the next setting decides. Spacing moves to M3's 4 dp grid in the same stack, delivering #854's "align Spacing" line. The migration ships as a seven-part stack with a temporary deprecated bridge; a Konsist test forbids colour, corner and font-size literals once it is gone.
- **Supersedes / Superseded-by:** Supersedes M38 D6. Narrows `apps/android/CLAUDE.md`'s "mirrors `apps/ios` 1:1 in behavior, tokens and funnel" — tokens no longer mirror.
- **Refs:** #853, #854, #858, #921, `docs/superpowers/specs/2026-09-24-android-m3-expressive-theme-design.md`, `apps/android/app/src/main/kotlin/app/pbbls/android/core/designsystem/ColorSchemes.kt`, `apps/android/app/src/main/kotlin/app/pbbls/android/core/designsystem/PebblesTheme.kt`.

## 2026-09-25 — Android chrome is stock Material 3; the controls stop mirroring iOS (#854)

- **Status:** taken
- **Scope:** android, ui
- **Context:** Every Android chrome primitive was a SwiftUI idiom rebuilt from `Box`, `Row` and `clickable` — primary button, top bar, text input, checkbox, auth switcher, glyph tabs, list cards, progress dots — and the accessibility gaps the audit found (no TalkBack action on the glyph slide, 44 dp targets ported from iOS points, "selected" announced where "checked" was meant, fixed heights under sp text) clustered in exactly those controls. #853 had just made the theme express the brand, so stock components could finally look like Pebbles.
- **Decision:** App code uses stock M3 (Expressive where it exists in the pinned `1.5.0-alpha27`) for chrome: `Button`/`OutlinedButton` with `ButtonDefaults.shapesFor`, `Checkbox` in `toggleable` rows, `OutlinedTextField`, `ListItem` in `OutlinedCard`, `Scaffold` + top app bars, a connected `ButtonGroup` for the auth switcher, a `HorizontalFloatingToolbar` of toggles for the glyph tabs, `FilterChip`/`RadioButton` in `selectableGroup`, `LinearWavyProgressIndicator`, `LoadingIndicator`. Wrappers are deleted rather than re-skinned unless a real Pebbles default repeats across call sites (`PebblesPrimaryButton`: full width + loading; `GoogleSignInButton`: the brand-mandated white container and G mark). The full-width funnel action height is the M3 medium button, `PebblesActionHeight` (56 dp). Controls with no stock equivalent stay custom and carry the semantics a stock one would: `SlideToConfirm` (button role, cost as state, TalkBack double-tap confirms, RTL-aware drag), `ValenceRoll`, the valence fan, and `NewPebbleButton` — kept because its long-press opens the all-at-once composer (M58 D1) and no stock button takes a long press.
- **Why:** Stock components carry 48 dp targets, ripples, roles, state descriptions, focus and error states for free; re-implementing each on a `Box` is how the gaps appeared, and re-skinning would keep paying for it. The glyph tabs are a floating toolbar rather than the `NavigationBar` #854 suggested because the store already sits inside the four-tab bar and the same control lives in the picker sheet.
- **Consequences:** **A fourth deliberate iOS divergence** after the four-tab bar, the `core/` split and the M3-evo theme: Android controls look and feel like Android controls; behaviour and funnel still mirror iOS and no data contract moves. Disabled buttons use M3's container treatment, not the iOS clear-with-outline look. The swap stacks as seven PRs, one component family each; screenshot references re-baseline per part. Drag math converts the physical pointer x through `core/designsystem/LayoutDirectionDrag.kt` so gestures follow the reading direction.
- **Supersedes / Superseded-by:** Extends **2026-09-24 — Android adopts the M3-evo Material 3 Expressive theme** from tokens to components.
- **Refs:** #854, #853, `docs/superpowers/specs/2026-09-25-android-stock-m3-components-design.md`, `docs/superpowers/plans/2026-09-25-android-stock-m3-components.md`.

## 2026-09-26 — Android adapts to large screens: readable column, navigation rail, phones stay portrait (#855)

- **Status:** taken
- **Scope:** android, ui
- **Context:** "Phone-only, portrait" was a doc claim, not a build fact: the manifest set no orientation or size restriction, so Play offered the app to tablets, foldables, ChromeOS and desktop windows, where every screen stretched to full width (timeline rows, pickers, the eleven-step record flow, pager pages past 800 dp). Android 16 ignores orientation and resizability restrictions at 600 dp and wider anyway, so a lock could never have kept the app off those screens.
- **Decision:** Android **targets** large screens rather than tolerating them. (1) Every screen's content is a column capped at 600 dp and centered (`Modifier.readableWidth()`, `core/designsystem/ReadableWidth.kt`): tab roots through `PebblesScreen`, whose top bar stays full-width; full-screen covers (detail, edit, create, record flow, drafts, invites, onboarding, welcome, auth) cap their whole root, top bar included, and read as a centered panel; Path caps its timeline only, so the FAB stays at the window corner. (2) The four-tab bottom bar becomes a navigation rail at 600 dp and wider, via `NavigationSuiteScaffold`. (3) The glyph store's floating toolbar moves from the bottom edge to a vertical toolbar on the end edge at the same breakpoint. (4) Phones are portrait-locked (`screenOrientation="portrait"`, with `LockedOrientationActivity` and `DiscouragedApi` suppressed inline), matching the iPhone-only iOS app; the lock is inert on large screens by platform rule. No `<compatible-screens>`.
- **Why:** The cap needs no size-class branch: below 600 dp it never binds, so phones render pixel-identical and only large windows change. A rail is what M3's adaptive scaffold prescribes once a bottom bar's reach stops matching how the device is held. Targeting rather than tolerating is what makes the rail and the end-edge toolbar worth building; list-detail Scenes are the next step and were split out rather than folded in.
- **Consequences:** Screenshot variants at 840 dp and 1024 dp (`@PreviewWide`, `@PreviewWideTall` in `PreviewVariants.kt`) cover Path, the record flow, Profile and Settings. A new screen must apply `readableWidth()` (or render through `PebblesScreen`) or it stretches on tablets. `ModalBottomSheet` already caps itself at 640 dp (`BottomSheetDefaults.SheetMaxWidth`), so sheets are left alone. iOS stays iPhone-only: this is an Android-only surface decision and moves no data contract.
- **Supersedes / Superseded-by:** Supersedes the "phone-only, portrait" framing in `apps/android/CLAUDE.md` and the `libs.versions.toml` note that `material3-adaptive-navigation3` has no call site because the app is portrait-locked.
- **Refs:** #855.

## 2026-09-26 — Android list-detail on large screens; pebble detail is a sheet on phones and a pane beside Path (#940)

- **Status:** taken
- **Scope:** android, ui
- **Context:** #855 made Android target large screens but stopped at one pane: on a tablet, opening a soul, a collection or a pebble still replaced the list it came from. M3's adaptive guidance is list-detail, with the rule that a pane **docked** on a compact window becomes **co-planar** on a large one. Pebble detail was a full-screen slide-up cover (the M38 D5 idiom, "input-opaque like the iOS fullScreenCover"), but iOS has since presented it as a sheet (`PathView` → `.sheet { PebbleDetailSheet }`).
- **Decision:** `RootScreen`'s `NavDisplay` tries a scene-strategy chain (`navigation/PebblesSceneStrategies.kt`): a list-detail strategy (the `adaptive-navigation3` `ListDetailSceneStrategy`, wrapped), then a bottom-sheet strategy (`navigation/BottomSheetSceneStrategy.kt`, the Nav3 recipe). Two panes from 840 dp, or at a separating vertical hinge (book posture), via `pebblesPaneDirective`. **Each detail keeps its iOS presentation on phones and becomes a co-planar pane on large screens:** soul and collection details stay pushes; pebble detail becomes a docked full-height sheet. `PebbleDetail` becomes a `BarKey`: the bar sits under the sheet's scrim on a phone and beside the panes on a tablet. Path stays full width until a pebble opens. List-detail back uses `BackNavigationBehavior.PopLatest`. Picking another item beside a list swaps the detail (`Navigator.navigateToDetail`), and deleting the item open beside its list closes it (`Navigator.closeDetail`).
- **Why:** The sheet is parity with iOS, not a divergence. `PopLatest` because the library default, `PopUntilScaffoldValueChange`, treats an idle list with its placeholder as equal to a list with a detail (`ThreePaneScaffoldValue.equals` ignores the destination) and so unwinds past the tab root into Path. The wrapper also refuses a "pair" with no list under it, so a collection opened from You stays a single-pane push. The book-posture rule exists because M3's directive gives a Medium window one pane whatever the posture, which lays a single pane across the fold.
- **Consequences:** **D6 of #852 still holds**: tab switching is reachable only from a `BarKey`, and `PebbleDetail` is no longer a modal; `EditPebble`, opened from it, still is. A pebble left open on Path when the user switches tab stays on Path's stack and is shown again on return; scene keys (`PanePair`) keep it out of other tabs' pairs, which `PebblesSceneStrategiesTest` pins over the flattened multi-tab entry list. A detail screen learns it is a pane only through a `showBack` parameter the entry provider derives from `LocalListDetailSceneScope`; screens never import the adaptive library. Tabletop posture and single-pane screens in book posture still span the hinge. Glyph detail follows in #940 Part 4.
- **Supersedes / Superseded-by:** Supersedes the full-screen cover of **M38 D5** for pebble detail only. Extends **2026-09-26 — Android adapts to large screens** (#855).
- **Refs:** #940, `docs/superpowers/specs/2026-09-26-android-list-detail-scenes-design.md`, `docs/superpowers/plans/2026-09-26-android-list-detail-scenes.md`.
